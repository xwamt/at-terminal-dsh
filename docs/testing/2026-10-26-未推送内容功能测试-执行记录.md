## 3. 发现的缺陷（3 个）

### 缺陷 1（真 bug，低危）：截断路径会切裂多字节字符

**现象**：`run_remote_command` 返回 3 万汉字（90 KB，超过 `maxOutputBytes` 64 KB）时，返回文本尾部出现 **1 个 `U+FFFD`**：
```
last 12 repr: '汉汉汉汉汉汉汉�\n```'
replacement chars: 1
```
**根因**：`ca5dca2` 修的是 `dsh/spill.js` 的 `safeCut()`（spill 路径防切裂代理对），但 **`truncated` 路径**（`RemoteCommandExecutor` 按 `maxOutputBytes` 字节切）没有等价保护。64 000 字节 ÷ 3 = 21 333.3 字 ⇒ 必然切在汉字中间。

**影响**：模型看到 `�`；若恰好切在关键字段上可能误读。不影响执行结果。

**复现**：`at_terminal_run_remote_command {command:"python3 -c 'print(\"汉\"*30000)'"}`，看返回尾部。

**建议**：把 `safeCut` 的 UTF-8 边界回退逻辑复用到截断点（向前退到 `0b10xxxxxx` 之前），或按字符而非字节计 `maxOutputBytes`。

**✅ 已修复**（`src/agent/RemoteCommandExecutor.ts`）：`OutputBuffer.text()` 不再直接 `toString('utf8')`，而是先过 `utf8SafeEnd()` —— 从末尾回退最多 3 个续字节，找到最后一个 lead byte，只有它的字节全部到齐才保留，否则整字丢弃。代价是最多丢 3 字节，换来不会出现无法解释的替换字符。
- 单测 `test/agent/RemoteCommandExecutor.test.ts` 新增 2 例：`cuts truncated output on a UTF-8 boundary…`（1200 字节 / 1000 上限 / 分两块投递，断言结果恰为 333 个完整汉字、字节数 999、无 `U+FFFD`）与 `keeps every byte when the cap lands on a character boundary`（上限 900 正好等于 300 汉字，断言 `truncated: false` 且一个字节不丢）
- **反向测试**：把 `text()` 改回 `buffer.toString('utf8')` → 新用例 FAIL（`expected … not to contain '\ufffd'`），恢复后 18 passed
- **真机复验**：重启加载新 `host.bundle.js` 后重跑 `print('汉'*30000)` → `FFFD count = 0`；末 24 字节 hex 为 `e6b189…0a606060`（完整「汉」+ 换行 + 代码围栏），`EF BF BD` 不存在

### 缺陷 2（文案/语义）：`backgroundConnectionAllowed=false` 的出路之一是假的

**现象**：99.92 没有活动面板终端时：
```
Error: SSH server "af238298-…" does not allow background connections.
Ask the user to enable "Allow background connections" on the AT Terminal server edit form,
or connect an AT Terminal session to that server.
```
**问题**：第二条出路「or connect an AT Terminal session to that server」**不可行** —— 我用 `terminal_open {type:"ssh", name:"99.94"}` 建了 pty-1（返回了 banner 和提示符），再打 `run_remote_command` 仍然报同样的错。判定范围只认**面板里的终端页签**，不认 host 侧 `terminal_*` 会话。

旁证：三台都在时，不传 `serverId` 的报错只列 **2 台**（99.90、99.92），pty-1 的 99.94 不在其中 —— 两处判定同源。

**影响**：agent 会反复尝试「连一个会话」这条死路；用户也难从文案看出「必须在面板里连」。

**建议**：文案改成「or open a terminal tab for that server in the AT Terminal panel」；或让 `terminal_open` 的会话也算作 connected（需改 `serverTarget` 的候选来源，属契约变更）。

**✅ 已修复（只改文案，不动契约）**（`AgentToolService.ts` 与 `SftpAgentService.ts` 两处同源文案）：
```
… or open a terminal tab for that server in the AT Terminal panel.
A `terminal_*` session does not count: the check reads the panel's own terminal tabs.
```
- 前缀 `does not allow background connections` 原样保留 —— `auditReasonForError` 靠它判 `background_denied`
- 单测 `AgentToolService.test.ts` 把断言从「只匹配前缀」改成三条：前缀仍在、新出路在、**旧死路 `connect an AT Terminal session to that server` 必须不存在**
- **反向测试**：把文案改回旧的 → 该用例 FAIL（`expected … to contain 'open a terminal tab…'`），恢复后 48 passed
- **真机复验**：99.94（`backgroundConnectionAllowed=false`、无面板终端）返回的正是新文案
- 未做「让 `terminal_open` 也算 connected」：那会改 `serverTarget` 的候选来源，属契约变更，留给你拍板

### 缺陷 3（轻微）：`npm run release --tag` 的 dry run 不预告 tag

dry run 在 gates 之前 `process.exit(0)`，`--tag` 分支在 publish 之后，所以计划里看不到 `v0.2.0`。行为安全（不会误打 tag），只是「prints the plan」对 tag 不成立。建议在 dry run 输出里加一行 `would tag v0.2.0`。

**✅ 已修复**（`scripts/release.mjs`）：抽出 `tagExists(name)`，dry run 在打印计划时补一行 —— 已存在打 `tag exists    v0.2.0`，否则打 `would tag     v0.2.0`。tag 步骤复用同一个判断，避免「计划说的」与「实际做的」分叉。
- **真机复验**：`npm run release -- --tag` 现在输出 `  tag exists    v0.2.0`（本机 `v0.2.0` 标签已存在）；`would tag` 分支与它共用一条三元表达式

## 8. 新缺陷（第二轮发现）：探针失败时 HUD 仍显示旧数字

**现象**：`ca5dca2` 的提交信息说「`HardwareMetricsCollector` read the empty stdout as 'the probe failed' and kept the cached numbers, which makes a wedged host look idle … the HUD shows a real failure」。但代码链路是：

```
HUD → monitor.metrics.get（channel.js:970）
    → agent.getHardwareMetrics(serverId)
    → HardwareMetricsCollector.getMetrics()
        try { execute(…timeoutMs:4000) ; if exitCode===0 && stdout → 解析并写缓存 }
        catch { /* Degrade gracefully on execution failure */ }   ← 超时落这里
        return cached ? cached.metrics : createFallbackMetrics()  ← 与成功时的返回值无法区分
```

**根因**：
1. 探针超时（`RemoteCommandTimeoutError`）被 `catch {}` 静默吞掉；
2. 返回 `cached.metrics` —— 上一轮的**真实数字**，比全 0 的 fallback 更容易让人误判成「机器很闲」；
3. `HardwareMetrics` 类型（`client/models.ts:1041`）**没有任何失败或过期字段**（只有 `serverId/timestamp/cpu/memory/disk/network/processes`），HUD 无法知道这批数字是新鲜的还是陈的。

**所以 `ca5dca2` 修到的是 executor 层（reject 而不是 resolve `exitCode:null`），collector 层的降级仍然静默。** 工具调用路径确实会记 `command_timeout`（T7.4 已验），但 HUD 轮询路径不会。

**影响**：host 卡住时 HUD 显示上一次的正常数字，看起来一切正常 —— 正是这条修复想消除的误判。

**复现**：让 99.90 的探针超时（`iptables` 丢包 / 挂起 `sh`），看 HUD 硬件页 —— 数字不变、无任何失败提示；同一时刻 `at_terminal_get_hardware_metrics` 会报 `command_timeout`。

**建议**（属契约变更，未擅自改）：
1. `HardwareMetrics` 加 `stale: boolean` + `fetchedAt: number`（或 `probeFailed: true`）；
2. collector 在 `catch` 与「exitCode≠0」两条路径上都标记，而不是只 return cached；
3. HUD 在 `stale` 时把数字灰显 + 显示「数据已过期（最后一次成功 HH:MM:SS）」。

改动会动到共享类型与 HUD 渲染，所以留给你拍板。
