## 1. 背景与目标

### 1.1 现状判断

插件已经把「怎么装一个 DSH 插件」做对了：双半、effect 归属、错误分层、设置 schema、9 项门禁。问题不在能力缺失，而在**只用了执行面、没用语义面**：

| 层 | 已用 | 空着 |
|---|---|---|
| 执行 | `ctx.tools`（15 个）、`ctx.webServer`（自建 HTTP/SSE/WS） | `ctx.jobs`、`ctx.terminals` |
| 语义 | — | `ctx.systemPrompt`、`ctx.commands`、`ctx.tools.guard()`、`tools/pre-execute`、`tools/result` |
| 交互 | `sidebarRightTabs`、`slots`、`shortcuts`、`locale` | `ctx.commandUi`、`settings.plugins.tab`、`ctx.userQuestions` |

由此派生出四类**可观察**的后果：

1. **事后无证据**：`AgentAuditLog` 写好了却从未被构造（`host.bundle.js` 里 `agent-audit.jsonl` 0 命中），「历史执行」只活在内存里（上限 50 条）。
2. **授权只在工具内部**：`get_hardware_metrics` 绕过命令策略直接跑远端脚本；任何新入口都自动绕过护栏。
3. **超时≠完成**：`run_remote_command` 超时只 `stream.close()`，远端进程仍在跑；模型重试即双执行。
4. **文档与实现互相打脸**：三档写授权在 DSH 侧只剩 `once`；`features*.md` 对「full trust 是否跳过敏感路径」两句相反；README 工具表列了不存在的 `sftp_copy`。

### 1.2 可验收的目标

| 目标 | 量化判据 | 度量方式 |
|---|---|---|
| 审计可追溯 | 每次 `at_terminal_*` 调用在 `<DSH_HOME>/at-terminal/agent-audit.jsonl` 留一行，命令已脱敏 | 一次真实调用后 `wc -l` + 比对 `redactSensitiveText` |
| 护栏在 registry 层 | 15/15 工具在 guard 覆盖表内；`trust: 'none'` 的服务器上，直接调服务（不经工具）仍被拦 | 静态断言 + 单测 |
| 长任务可中断 | 后台 `sleep 60` 能被 `job_kill` 真正终止远端进程 | pidfile 校验 |
| 常驻 token | 工具定义体积 从 **7 811 B → ≤5 400 B**（−31%，按 §0.6 口径） | `createTools()` 序列化 |
| 启动载荷 | `client.js` 从 **1 022 198 B** 收敛——**目标值取决于 S4-03 的探路结论**：若 `immediately:false` 有收益则 ≤400 000 B（xterm 分块），否则如实记录「不可通过该开关收敛」 | 产物字节数 + `web boot` Network |
| 文档一致 | 工具表集合相等；三档授权与实现一致；版本号与实际宿主一致 | 3 条新测试 |
| 门禁可信 | B1/B2/B3 修复后，「9/9」才代表真实契约 | 门禁输出含宿主版本 |

- **现状证据**：
  - `package.json`：`verify:dsh` 与 `verify:kernel` 两个 script **字符串完全相同**；
  - `scripts/verify-kernel-seam.mjs` **不存在**，`src/platform/dsh/host.ts:11` 与 `dsh/README.md:113` 却都在引用它；

### S2-01 `tools.guard()` + `tools/pre-execute` 承载授权红线

- **优先级/估算**：P1 / M（2d）
- **目标**：让护栏落在 registry 层，任何新工具 / 新入口自动继承；落地迁移计划里的 DSH-35 / DSH-36。

- **接口**：
  - `ctx.tools.guard((exec) => string | undefined)`：同步、单调、不可翻盘；返回字符串即 deny；
  - `ctx.on('tools/pre-execute', async (exec, next) => …)`：`{kind:'allow'}` / `{kind:'deny',reason}` / `{kind:'ask',reason,displayReason}` / `{kind:'cancel'}`；`ask` 由 registry 走 `ctx.approval`，只有 `allowed-once` 放行；**不能**改写 `exec.arguments`。
- **实施步骤**：
  1. `dsh/policy.js`（新建）：一张**静态覆盖表**，列出 15 个工具各自的风险类别（`read` / `write-remote` / `destructive` / `ui`），并导出 `guardReason(exec)` 与 `preExecute(exec)` 两个纯函数（便于单测，不依赖 ctx）。
  2. `guard`：只承载**不可撤销**判定，且必须同步可得：
     - `at_terminal_sftp_delete` 在敏感路径上 deny（"sensitive path requires an explicit human decision; this tool never auto-approves"）；
     - 声明 `recursive` 之后的目录删除同理；
     - **不要**在 guard 里查服务器配置（那是 I/O）。
  3. `pre-execute`：承载可协商判定：
     - 从 `exec.arguments.serverId` 取服务器；取不到就 `next()`（读工具允许隐式目标，见 S5-01 的选择器）；
     - `agentCommandTrust === 'full'` → allow；`'policy'` → 跑 `authorizeRemoteCommand`，`autoApprove` 则 allow，否则 `{kind:'ask', displayReason: formatRemoteCommandConfirmMessage(...)}`；`'none'` → `ask`；

  5. 敏感路径**策略决定**（与 S1-03 的文档断言一起定）：本计划选择 **full trust 仍然二次确认敏感路径**（符合迁移计划 DSH-36 的原话与 `docs/features.zh-CN.md:82`）。实现方式：`SftpWriteAuthorizer.requireWrite` 把 `shouldAutoApproveSftpWrite` 的短路**移到敏感判定之后**。

## 5. S3 不阻塞（P1）

### S3-01 `run_remote_command` 支持后台执行

- **优先级/估算**：P1 / M（2d）
- **目标**：超时不再等于「进程还在跑但 Agent 以为失败」。
- **现状证据**：`RemoteCommandExecutor` 的 timeout 只 `stream.close()`（`:115-119`）；`finish(null)` 返回 `timedOut: true`，远端进程无人管。
- **接口（真实签名，逐字核对过）**：
  ```js
  ctx.jobs.start({
    kind: 'ssh-command',
    label: command,
    toolCall: { callId, rootCallId },
    owner: exec.agent?.session.id,          // 注意：owner 传的是 session id 字符串
    outputLimitBytes?, output?: Source[],
    run: (handle) => ({
      cancel: (reason) => void,             // 必须同步可调
      done: Promise<{ status: 'completed'|'killed'|'failed', detail: string }>
    })
  }) // → { id }
  ```
  控制面：`ctx.jobs.wait(id, timeoutMs, ownerSessionId, signal)` / `.kill(id, caller, reason)` / `.remove(id, caller)`；访问围栏 `job.owner.id !== caller` 会抛。
- **实施步骤**：
  1. `dsh/tools.js`：`run_remote_command` 增参数 `run_in_background: boolean`（默认 false）。**不改**现有参数语义。
  2. 后台分支：`ctx.jobs.start(...)`，`run(handle)` 里起一次 `executor.execute`，把 stdout/stderr 增量 `handle.append(text, { channel: 'stdout' | 'stderr' })`（`OutputRing.append(text, options, cap)` 只认 `channel` 与 `gapBefore` 两个字段，`jobs-lib.js:205-219`）；`cancel(reason)` 里对远端进程发 `SIGTERM`（见 3）。
  3. **真正杀掉远端进程**：现有 executor 只有 `stream.close()`。改为在命令前包一层 `sh -c 'echo $$ > /tmp/.at-<id>.pid; exec <cmd>'`，超时/取消时通过**同一条 SSH 连接**发 `kill -TERM -<pgid>`。这是本任务唯一的领域层改动，必须在 `RemoteCommandExecutor` 里加可注入的 `onPidKnown` / `terminate` 钩子，保持 VS Code 变体行为不变。
  4. 前台分支不变（默认路径零风险）；当 `timeoutMs > 30_000` 且用户未显式要求后台时，**不自动转后台**（隐式行为会让模型困惑），只在结果里提示「可用 run_in_background 重试」。
  5. `job_kill` 的语义：`kill` → `done` 结算为 `killed`，远端进程已被 SIGTERM。
- **DoD**：
  - `sleep 60` 后台运行 → 返回 `{kind:'background', jobId}` → `job_kill` 后**远端** pidfile 中的进程消失；
  - 前后台输出量一致（同一命令各跑一次比对）；
  - 无 `ctx.jobs` 的组合（preset 关掉 `tool-jobs`）自动降级为前台并返回可读原因，不抛。
- **测试/验证**：`test/dsh/jobs.test.ts`（新建，fake `ctx.jobs` + fake executor，≥8 例）；真实远端验证用一台可丢弃主机，记录 pidfile 前后。
- **风险/回滚**：`jobs.start()` 在无 controller 时抛「no job controller serves this agent」——**必须 catch 并降级**，否则 `minimal` preset 直接不可用。回滚：删除 `run_in_background` 参数（schema 收窄），代码路径保留在 `dsh/jobs.js`。

### S5-01 恢复三档写授权（`ctx.userQuestions`）

- **优先级/估算**：P2 / M（1.5d）
- **现状证据（文档-实现漂移）**：`SftpWriteAuthorizer.resolveAllowedScopes()` 仍算 `['once','directory','session']`，`docs/features.md:77` 与 `:80` 也这么承诺；但 `DshAgentConfirmation.confirmSftpWrite` 把 `approval.request()` 的四种结果**统一映射为 `'once'`**（`confirmation.ts:110`），`ctx.approval` 词汇本就没有「记住范围」。
- **接口**：`ctx.userQuestions.ask({ questions:[{ id, question, header?, options:[{label,description?}], multiSelect? }], agent, signal })` → `{ answers:[{ id, selected:[label], custom? }] }`；`ask` 只接受 **root agent**，子 agent 会以 `DELEGATED_CALLER` 拒绝。
- **实施步骤**：
  1. `confirmSftpWrite` 分两段：先用 `userQuestions.ask` 选范围（`仅本次` / `此目录 15 分钟` / `本会话`，与 `allowedScopes` 一一对应），再把结果回填 `SftpWriteScope`；
  2. 敏感路径与越界路径**不提供**「本会话」选项（与 `resolveAllowedScopes` 的既有分支一致）；
  3. 删除路径、敏感路径二次确认仍走 `ctx.approval`（只有是/否）；
  4. 无 responder（`NO_PROVIDER`）时降级为 `'once'`，并 `logger.warn` 一次——**不要**让写操作因缺少 UI 而失败。
- **DoD**：选「此目录 15 分钟」后同目录第二次写不弹窗、跨目录弹窗且无「本会话」；子 agent 调用时给出可读指引而不是崩。
- **测试/验证**：`test/platform/dsh/confirmation.test.ts` 增 6 例（三档 × 有/无 responder）。
- **风险/回滚**：`userQuestions` 在不带 agent 的调用里会 `NO_PROVIDER`；所有调用点必须能承受降级。

### S5-04 多服务器时的显式目标（R10b + R14③）

- **优先级/估算**：P2 / S（0.75d）
- **目标**：多台服务器都活着时，Agent 不能靠「最近连接的那台」猜。
- **现状证据**：`AgentToolService.resolveServer`（`:414-441`）在 `serverId` 省略时取 `terminalContext.getConnectedTerminal()`（**最近连接的活终端**）；只有「没有任何活终端」时才抛 `serverId is required…`。于是「三台连着，Agent 想查 B 却没传 serverId」会静默打到最近那台——**结果看起来像成功**。
- **接口**：与 S5-01 同一个 `ctx.userQuestions.ask(...)`；`agent` 必须是 root（`DELEGATED_CALLER` 会拒）。
- **实施步骤**：
  1. `resolveServer` 分三种情况：
     - 显式 `serverId` → 直接用（现状）；
     - 省略 + **恰好一台**活终端 → 用它，但结果里回显 `resolvedBy: 'single-connected'`；
     - 省略 + **多台** → 不再静默挑选：**读类工具**（list/stat/read/metrics/terminal-context）仍允许隐式（便利性优先，且无副作用），但返回值必须带 `resolvedBy: 'implicit'` 与 `candidates: [ids]`；**写类与执行类**（write/create/createDir/rename/delete/run_remote_command/open_monitor）直接抛一条**列出候选**的错误，让模型带 `serverId` 重试——不弹问人，因为这是模型可以自己修正的参数错误。
  2. 只有当调用来自**交互式会话**且模型连续两次猜错时，才升级为 `ask()` 选择器（避免每次都打断用户）。
  3. `dsh/tools.js`：给上述 6 个工具的 `serverId` 参数描述补一句「Required when more than one server is connected」。
  4. 审计（S1-01）里记录 `resolvedBy`，事后能查出「这次打到哪台、怎么定的」。
- **DoD**：
  - 三台连接时 `sftp_write_file` 不传 `serverId` → 错误消息列出 3 个 id 与 label，**不执行**；
  - 同一场景 `sftp_read_file` 不传 → 成功且结果含 `resolvedBy: 'implicit'` + `candidates`；
  - 一台连接时不传 → 成功且 `resolvedBy: 'single-connected'`；
  - `tools.test.ts` 增 3 例覆盖三种情况。
- **测试/验证**：`test/agent/AgentToolService.test.ts`（3 例）、`test/dsh/tools.test.ts`（`resolvedBy` 出现在 schema 与 render 里）。
- **风险/回滚**：写类工具变严格会让**已有的单服务器用法不受影响**、但「多服务器 + 省略 serverId」的老用法会从「静默成功」变成「报错」。这是**有意的行为变更**，发布说明必须写明；回滚方式是放松为一律允许隐式 + 只打 `resolvedBy` 标记。

### S6-01 / S6-02 持久 SSH 会话（opt-in bundle）

- **优先级/估算**：P2 / L（4d）
- **接口**：`ctx.terminals.registerBackend({ type, spawn, read, send, signal, close, status })`；消费方是官方 6 个 `terminal_*` 工具（`terminal_open/send/read/signal/close/list`），带 owner 隔离（`FOREIGN_SESSION`）与 `run_in_background` job 集成。
- **S6-01（bundle 骨架）**：新建 `cordis.patch.yml` 层，照抄 `dsh-experimental-terminal-bundle/cordis.patch.yml` 的结构（`cordis:group` + `isolate: { terminals: true }`，内含 `dsh-terminal` + 本插件的 `ssh` backend + `dsh-tool-terminal`）。**顺序必须是注册表→backend→工具**。
- **S6-02（backend 实现）**：`type: 'ssh'`，`spawn(spec)` 复用 `createDshTerminalApi(...).open()`；`send` 的就绪判定（`stdin_read`/`inferred_idle`/`timeout`/`session_exit`）直接映射 `SshSession` 输出流，**不要**自造等待语义。
- **DoD**：`terminal_open({type:'ssh'})` 后连续两次 `terminal_send` 的 `cd` 生效；owner A 拿不到 owner B 的 session id；缺 `ctx.terminals` 时本插件原有能力完全不受影响。
- **风险**：`desktop` 组合**默认不挂** `ctx.terminals`，必须由本插件插入；`api-terminal-controller`（右栏本地终端）**不消费** `ctx.terminals`，所以这条**不会**替换现有 UI——纯增量。
