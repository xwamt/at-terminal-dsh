## 0. 结论先行

| 问题 | 结论 | 证据 |
|---|---|---|
| dsh 是否支持多终端/多会话？ | **支持，且是一等公民**。官方 `terminal` 类型以 `multiple: true` 注册，每次打开铸独立 contentId | sidebar-terminal `client.js:438-451`、sidebar-right `client.js:6470` |
| 有硬性上限吗？ | **有**：`maxTerminals` 默认 **8**（"Retained terminals and pending allocations per Session"）。另有 `maxCols/maxRows=500/200`、`scrollback=1000`、`maxBufferedBytes=2MiB` | api-terminal-controller `README.md` 配置表 |
| 那个上限管我们的 SSH 会话吗？ | **不管**。`maxTerminals` 属官方 `api-terminal-controller`（本机 shell 用 `ctx.subprocess.spawnTerminal`）。我们的 SSH 会话走自己的 `/dsh-at-terminal/ws`，宿主侧 `live` 是**无上限**的 `Set<SshSession>` | services.ts:366,463；channel.js:989 |
| 切标签会不会掐掉会话？ | **官方不会，我们会。** 官方靠"window hold（`retain` 流）"把进程保住，与 React 挂载解耦；我们的 socket 活在 React 组件里，组件卸载即断 | api-terminal-controller `README.md`「Understand the implementation」；body.ts:800-802 |
| 「新建终端」按钮是不是没生效？ | **按钮是生效的，但它做了错的事**。真实日志证明新标签确实开出来了，只是空落到服务列表页；同时旧标签的会话被卸载掐断 | `~/.dsh/at-terminal/client-diagnostics.log`（§4.3） |
| 现有多标签能力 | 已具备（`multiple: true` 已构建进产物） | main.ts:292；`dsh/client.js` 含 `multiple: !0` |

一句话：**dsh 侧没有挡路的东西，挡路的是本插件把自己的会话生命周期拴在了 React 组件上。**

## 2. 调研结论：dsh 的多会话模型

### 2.1 官方 `terminal` 类型就是一个「多实例页类型」

```js
// dsh-client-ui-sidebar-terminal/lib/client.js:438-451
ctx.sidebarRightTabs.register({
  id, kind: "terminal",
  multiple: true,                 // ← 关键
  priority: "builtin",
  title: () => t("title"),
  guide: [{ id: "new", order: 20, title: () => t("new"), description: () => t("description"), icon: PluginArtworkTerminal }]
})
```

`multiple: true` 的作用点在 `placeTab`：

```js
// dsh-client-ui-sidebar-right/lib/client.js:6467-6476
placeTab(sessionId, actions, kind, options) {
  const definition = this.tabs.get(kind);
  if (definition === void 0) throw new Error(`sidebarRight: no tab type is registered as "${kind}"`);
  const address = definition.multiple === true ? `${pageAddress(kind)}/${randomUUID()}` : pageAddress(kind);
  this.place(sessionId, actions, { kind, contentId: address, title: definition.title(address) }, address, options, options.params);
}
```

即：**不带 `multiple` 的页类型每次打开都落到同一个固定地址，侧栏视其为同一页；带 `multiple` 的每次铸一个新 UUID 地址，因此是并列的独立实例。**

我们的插件**已经**设了这个标志（`src/platform/dsh/client/main.ts:292`），并且已构建进产物（`dsh/client.js` 中含 `multiple: !0`）。所以「同时开多个终端」这一层，dsh 侧从来没有拦过。

### 2.2 官方会话模型：`api-terminal-controller`

| 事实 | 原文/证据 |
|---|---|
| 远程 API 面 | `remote.terminal` 暴露 `environment`、`shells`、`list`、`create`、`retain`、`follow`、`write`、`resize`、`rename`、`close`；**每个操作按 Session 身份隔离** |
| 会话上限 | `maxTerminals` 默认 `8` —— "Retained terminals and pending allocations per Session" |
| 输出保留 | `scrollback` 默认 `1000` 行；`maxBufferedBytes` 默认 `2097152`（单个 follower 的待发队列） |
| 空闲回收 | `unattendedTimeoutMs` 默认 `7200000`（2 小时），**且只在最后一个 window hold 消失后才计时**；`0` 表示关闭自动回收 |
| 输入独占 | "Only one attachment at a time can write or resize."（同一时刻只有一个附着端可写/改尺寸） |
| 插件卸载 | "Plugin disposal awaits active and previously detached output streams **without closing Host processes**." |
| 极端情形 | "Exited terminals count toward `maxTerminals`; close unused tabs to release their screens and quota." |

**对我们的直接含义**：`maxTerminals=8` 是官方**本机 shell** 终端的配额，与我们的 SSH 通道无关（我们的宿主 `createDshTerminalApi` 用 `new Set<SshSession>()` 记录活会话，见 `src/platform/dsh/services.ts:366`，`terminalId` 每次 `randomUUID()`，见 `:463`，**没有任何数量上限**）。

但「一个附着端独占输入」「插件卸载不关进程」这两条**设计原则**是我们要对标的，我们目前两条都不满足。

### 2.3 会话存活靠的是「window hold」，不是 `keepMounted`

官方 `terminal` 的**进程存活**链路是：

```
sidebar 的完整已开标签清单
      ↓（intersect）
Client 自己保存的 contentId → Host terminalId 绑定（localStorage: dsh.terminal.binding.v1.*）
      ↓
remote.terminal.retain(sessionId, id, signal)   ← 独立的 Remote 流，只声明"这个窗口还留着它"
      ↓
Host 侧一旦还有 hold 就不回收进程
```

原文（api-terminal-controller `README.md`）：

> An open tab in any connected window retains its terminal, **including hidden tabs and inactive Sessions**. …
> The Client saves each Session/content-to-terminal association before allocation under its own `dsh.terminal.binding.v1.*` localStorage key. **The content identity is globally unique; layout-local tab ids only identify live view occurrences.**
> The separate `retain(sessionId, id, signal)` Remote stream acknowledges a window hold **without Agent activation, screen output, input transfer or process creation**.

所以官方终端的进程**不随 React 渲染树存活**——它的模型注册表在 React 之外（`ctx.webTerminals`，即 `api-terminal-controller` 的 React-free 模型），标签被隐藏时只是**不渲染**，不是**不存在**。

再看 `keepMounted` 是干什么的：

```js
// sidebar-right/lib/client.js:5551-5560（TabSlot）
const retained = seat === "sidebar.right.pane.tab" && definition?.keepMounted === true;
useLayoutEffect(() => retained ? retainTab(tab.id, signal) : void 0, [retained, retainTab, tab.id, signal]);
// sidebar-right/lib/client.js:5730（DockLayout）
keepMounted: (tab) => types.find((type) => type.kind === tab.kind)?.keepMounted === true
```

`keepMounted` 管的是**DOM/React 本体要不要保留**（保留者被搬进隐藏子树），而进程存活由 `retain` hold 负责。官方 `terminal` 类型**不设** `keepMounted`，却仍能保住进程——因为它把模型放在 React 外。

这段结论解释了我们 `main.ts:294-315` 注释里那段历史困惑：当时观察到「设了 `keepMounted` 面板闪一下变白」，于是**把它和"会话存活"一起放弃了**。正确的结论是：**`keepMounted` 确实不是会话存活的工具（放弃它是对的），但会话存活必须另找载体（React 外的注册表），而不是顺带放弃。**

### 2.4 内容身份：用 `contentId`，不是 `tab.id`

- layout 里的 tab 记录含 `contentId`（`sidebar-right/lib/client.js:4944` schema：`contentId: string().min(1)`），由 `actions.openContent({ kind, contentId, title, … })` 写入（`:6473-6487`）。
- 官方 `useTabInfo()` 返回：

```js
// sidebar-right/lib/client.js:8965-9001
return {
  sidebar: { expanded, fullscreen },
  panel: { id: pane.id },
  tab: { ...tab, visible, navigation, signal, actions, refreshShortcut }
};
```

`tab.navigation` 是 TabDomain occurrence 的导航对象，`getSnapshot()` 给出 `{ address, params, revision }`。

**`contentId` 是全局唯一的内容身份，`tab.id` 只是布局局部的实例 id**（README 原话）。因此：

| 用途 | 正确键 |
|---|---|
| 标签 chip 徽标（绑 live 实例） | `tab.id`（现状正确） |
| **会话注册表 / 文件树绑定 / 关闭清理** | **`contentId`**（现状**未使用**） |

### 2.5 给新标签传参：`openTab(kind, { params })`

官方在 guide 里选完 shell 是这么开的：

```js
// sidebar-terminal/lib/client.js:133-136
tab.actions.openTab("terminal", { replaceTab: true, params: { shellPath: path } });
```

读回来：

```js
// sidebar-terminal/lib/client.js:375-383
const target     = (sessionId, key) => ctx.sidebarRight.tabDomain.occurrence(sessionId, { id: key }).navigation.getSnapshot().params;
const terminalId = (sessionId, key) => { const params = target(sessionId, key); return params !== void 0 && "terminalId" in params ? params.terminalId : void 0; };
const view       = (sessionId, key) => {
  const params = target(sessionId, key);
  const contentId = ctx.sidebarRight.tabDomain.occurrence(sessionId, { id: key }).navigation.getSnapshot().address;
  return ctx.webTerminals.view(sessionId, key, contentId, terminalId(sessionId, key), params !== void 0 && "shellPath" in params ? params.shellPath : void 0);
};
```

`params` 的落点与 `openTab` 的选项全集：

```js
// sidebar-right/lib/client.js:6478-6507（place）
this.tabDomain.navigate(sessionId, tabId, { address, params });
```

| `openTab` 选项 | 语义（sidebar-right `client.js:6478-6507`） |
|---|---|
| `params?` | 导航参数，落到 `tab.navigation.getSnapshot().params` ← **我们要用的** |
| `replaceTab?` | 用新标签替换该 tab 的位置（优先于 `preferNewPane`） |
| `revealIfOpened?` | 默认 `true`：已有同 `(kind, contentId)` 则聚焦而非新开；页类型只在目标格内去重 |
| `preferNewPane?` | 先尝试分栏（两格上限），失败回退目标格 |
| `paneId?` | 指定停靠格 |
| `kind?` | 仅 `openResource` 用 |

**注意**：因为 `multiple: true` 每次铸新 UUID，`revealIfOpened` 在页类型上**永远不会命中**——所以我们的「新建终端」每次都是真·新标签。这与日志证据一致。

**时序保证（重要）**：`params` 在 body **首帧**就已可读，不需要轮询或延迟：

```js
// sidebar-right/lib/client.js:6114-6136
/**
 * Record that an `open` settled on a tab.
 *
 * A record the layout has not yet shown the seat gets its occurrence here,
 * so **the body's first render already carries the opener's `params`**.
 */
navigate(sessionId, tabId, target) {
  const existing = this.session(sessionId).get(tabId);
  if (existing === void 0) { this.hold(sessionId, tabId, { ...target, revision: 1 }); return; }
  existing.navigation.set({ ...target, revision: existing.navigation.getSnapshot().revision + 1 });
}
```

且 `useTabInfo()` 在 `navigation === undefined` 时直接 `throw`（`:8973`），即 body 根本不可能早于 navigation 渲染。所以「首挂载读 `params.serverId` 并自动连接」这条路是**安全**的。

### 2.6 关闭是显式的：`registerCloseHandler`

```js
// sidebar-terminal/lib/client.js:452-454
ctx.effect(() => ctx.sidebarRight.registerCloseHandler("terminal", (sessionId, tab) => {
  ctx.webTerminals.close(sessionId, tab.id, tab.contentId, terminalId(sessionId, tab.id));
}), "ui-sidebar-terminal.close");
// sidebar-right/lib/client.js:6345-6351（同 kind 二次注册 throw）
```

官方把「关标签 → 结束进程」放在**关闭钩子**里，而**不是**在 React 卸载里。这是「切换 ≠ 结束、关闭 = 结束」这条语义的实现方式 —— 正是我们要的 G3。

| 面 | 位置 | 用途 |

### 2.8 限制清单（本插件需要知道的）

| 限制 | 值/条件 | 是否影响我们 |
|---|---|---|
| 官方 shell 终端并发上限 | `maxTerminals = 8` / Session | ✗ 不影响（不是同一条通道） |
| PTY 尺寸上限 | `maxCols/maxRows = 500/200` | ✗（我们自管 ssh2 通道尺寸） |
| 一次只有一个输入独占者 | "Only one attachment at a time can write or resize" | △ 我们的模型是「一标签一 socket 一会话」，天然独占；但若日后做「同会话双视图」需处理 |
| 同 kind 只能一份 `builtin` + 一份 `extension` | `coexists`（sidebar-right `client.js:8631-8632`） | ✓ 我们取自己的 kind `at-terminal`，无碰撞 |
| 同一 `id` 重复注册 tab 类型 → throw | `:8696` | ✓ 已规避 |
| 同一 kind 二次注册 close handler → throw | `:6346` | △ 新增 close handler 时必须只注册一次（放 `ctx.effect` 内即为一次） |
| 同一 code 的快捷键默认值重叠 → throw 并使整个插件加载失败 | 见 main.ts:107-126 的历史事故 | ✓ 已规避（`web:*` 故意留空） |
| `DockLayout` 同格标签数 | 无硬上限；`canSplit` 限两格，`minPaneFraction 0.2` | △ 标签多了只能水平滚动，无自动溢出菜单 |

## 3. 现状与「新建终端」根因

### 3.1 现状链路（逐跳）

```
views/terminal.ts:192-202  「新建终端」按钮 onClick: props.onNewTab
        ↓
body.ts:1157               onNewTab: openNewTab
        ↓
body.ts:343                openNewTab = props.openNewTab
        ↓
main.ts:403                wrapWithLocale(AtTerminalBody, t, { openNewTab })
        ↓
main.ts:372-381            ctx.sidebarRight.openTab(KIND)      ← 无 params
        ↓
sidebar-right:6467-6476    placeTab → multiple:true → 新 UUID contentId
        ↓
新标签 body 挂载 → mode 初值 'assets' → 落在服务列表页
```

结论：**按钮没有坏，它精确地执行了「开一个属性全空的新标签」。**

### 3.2 三个真实缺陷

| # | 缺陷 | 位置 | 后果 |
|---|---|---|---|
| **D1** | 新标签不带任何上下文，`mode` 初值 `'assets'`、`selectedServerId` 初值 `''` | body.ts:347、:393；main.ts:372-381 | 用户看到的是「服务列表 + 未选择」，读作"又让我选一次连接" |
| **D2** | 会话（socket + `SshSession`）生命周期绑在 React 组件上；未设 `keepMounted`，切到别的标签即卸载 | body.ts:418-430、:673-705、:800-802；main.ts:294-315 | **旧标签的 SSH 会话被掐断**；切回来重建连接（`services.ts` 里那条 `live.delete(session)` 由 socket 关闭触发） |
| **D3** | 徽标注册表在卸载时被清（`clearTabBadge`），且没有任何关闭钩子 | body.ts:162-178、:454-466；main.ts 全文件无 `registerCloseHandler` | 切换后原标签 chip 失去「连的是哪台」，两条终端变得无法区分 —— 恰是徽标当初要解决的问题；关标签也没有显式通知宿主 |

### 3.3 缺陷链的宿主侧闭环（为什么 D2 会真的掐断 SSH）

```
浏览器 body 卸载
   → teardown(false)                       body.ts:673-705
   → socket.close()                        body.ts:700-704
   → 宿主 socket close 处理器
   → closeTerminals(session)               dsh/channel.js:1098-1108
   → terminal.close()                      → SshSession.dispose()   services.ts:477-484
   → observer.closed(terminalId)           sftp.ts:373-383 → SftpManager 置 disconnected
```

注意宿主侧 `session.terminals` 本身是个 **Map**（`dsh/channel.js:989`），**一个 socket 支持多个 terminal**——能力上够用，缺的是「谁来持有 socket」。

## 5. 实现方案

### 5.1 目标拆解（可验收）

| 编号 | 目标行为 |
|---|---|
| **G1** | 点「新建终端」→ **立刻**出现新标签，并**自动**接上（默认沿用当前标签的连接目标，或由调用方指定服务器） |
| **G2** | 多个终端**同时在线**；切换标签**不掐会话**，切回来仍在原处（含已滚出的输出尽量保留） |
| **G3** | **关闭标签 = 结束会话**；**切换标签 ≠ 结束会话**（两条路径必须分开） |
| **G4** | 文件页只反映**本标签**的终端；两个标签并发读目录**不串台** |
| **G5** | 标签 chip 能区分「连的是哪台」，且该信息不因切换而丢失 |

### 5.2 两条路线

| | 路线 A：浏览器侧会话注册表 | 路线 B：宿主侧会话仓库 |
|---|---|---|
| 载体 | 客户端模块级 `Map<contentId, TabSession>`，持有 socket/flow/缓冲/状态 | 宿主 `Map<contentId, {...}>` + 新增 RPC `session.*` |
| 卸载语义 | `detach`（socket 不断） | `detach`（socket 可断，宿主保会话） |
| 跨标签存活 | ✅ | ✅ |
| 刷新页面后恢复 | ❌（重连） | ✅（对齐 `dsh.terminal.binding.v1.*`） |
| 宿主改动 | 无（除 §5.4 的并发修复） | 大：屏幕快照/有界重放/空闲回收/关闭请求持久化 |
| 风险 | 脱离期输出需有界缓冲 | 重构面大，需重做验收基线 |
| 工作量 | 中 | 高 |

**推荐：本轮落 A（L1+L2+L3），B 单独立项。** 理由：用户的核心诉求是「同时连接并切换多个终端」——A 已完全满足；B 的额外收益只是「刷新页面也活着」，而刷新重连本就是我们今天已有的行为，不是回归。且 A 设计的 `sessions.ts` 天然就是 B 的客户端外壳：届时把 `TabSession` 里的 `WebSocket` 换成 `session.attach` RPC 即可，React 侧与文件树侧不用再动。

### 5.3 分层落地

#### L1 —— 让新标签「自动接上」（修 D1，G1）

1. **`main.ts`**
   - `openNewTab` 签名改为 `(serverId?: string) => void`。
   - 调用改为 `ctx.sidebarRight.openTab(KIND, serverId === undefined ? undefined : { params: { serverId } })`。
   - `ShortcutCommand.resolve` 的 `run` 改为 `() => openNewTab(currentServerId())` —— 快捷键也沿用当前标签的目标。
   - **默认值策略（需你确认）**：建议「沿用当前焦点标签已连接的服务器」，而不是全空。若希望保持"空标签"语义，则改为只传 `params: { auto: 'last' }` 让 body 自己决定。
2. **`body.ts`**
   - 新增 `readTabParams(props): Record<string, unknown>`：读 `useTabInfo().tab.navigation?.getSnapshot?.().params`，`try/catch` 兜底 `{}`（与 `readTabId` 同一防御姿态，且**必须**在组件顶层调用，不可放进 `useState` 初始化器——见 `readTabId` 的 React #311 注释）。
   - 首次挂载时：若 `params.serverId` 是已知服务器 → `setMode('terminal')` 并 `doConnect(serverId)`；只做一次（`useRef` 闩锁），避免每次重渲染重连。
   - 「新建终端」按钮的语义从"开一个空标签"变为"以当前连接为模板再开一个"，并在按钮 `title` 里说明。
3. **`views/terminal.ts`**
   - `onNewTab` 类型改为 `(serverId?: string) => void`；按钮 `onClick: () => props.onNewTab(props.selectedServerId)`。

验收：点一次 → 新标签直接进入 terminal 页并出现连接中→已连接，**不出现服务列表页**。

#### L2 —— 会话移出 React（修 D2/D3，G2/G3/G5）

新增 `src/platform/dsh/client/sessions.ts`：

```ts
export interface TabSession {
  readonly key: string;                 // = tab.contentId
  readonly hostTerminalId: string;      // 由 terminal.opened 学到
  state(): TerminalSessionState;
  error(): TermError | null;
  attach(engine: TerminalEngine): void; // 挂上渲染端，回放缓冲
  detach(): void;                       // 摘掉渲染端，保留 socket
  write(data: string): void;
  resize(rows: number, cols: number): void;
  subscribe(listener: () => void): () => void;
  close(notify: boolean): void;         // 真正结束
}
export function getSession(key: string, options): TabSession;
export function closeSession(key: string): void;
```

要点：
- **键用 `tab.contentId`**（§2.4），不是 `tab.id`，也不是常量 `TERMINAL_ID`。`terminal.open` 的 `id` 字段也改传 `contentId`（宿主 `session.terminals` 是 Map，天然支持）。
- socket、flow controller、`hostTerminalId`、`termState`、`termError`、`trusted` 全部从 `body.ts` 的 `useState/useRef` 搬进 `TabSession`；`body.ts` 改为**订阅**这些值。
- 脱离期输出进**有界环形缓冲**（建议 256 KiB 或 2000 帧，取小者），超限丢最旧并置一个"输出已截断"标记——诚实优于假装完整。
- **`teardown` 不再由 React 卸载调用**：卸载只 `detach()`。
- 显式关闭走关闭钩子（官方同构）：
  ```ts
  ctx.effect(() => ctx.sidebarRight.registerCloseHandler(KIND, (_sessionId, tab) => {
    closeSession(String((tab as { contentId?: unknown }).contentId ?? ''));
  }), 'at-terminal: close handler')
  ```
  仍需在 `ctx.effect` 内注册（注销即解绑）。
- **不**引入 `keepMounted`（§2.3 已证它不是会话存活的工具，且历史上有白屏事故）。
- `ctx.effect` 的插件卸载回调里统一 `closeAllSessions()`，避免卸载插件留下孤儿 SSH 会话。

验收：两个标签各连一台；来回切换 5 次 → 两台都不断线、`bash` 的 `history` 连续；关闭其中一个 → 只有它断；宿主侧 `live` Set 计数与打开标签数一致。

#### L3 —— 文件树按终端绑定 + 修宿主并发（G4）

现状已有 `params.terminalId` 这一层，但宿主侧有一个**真实的跨标签串台面**：

```
src/platform/dsh/sftp.ts:387-421  list()
  followTerminal(terminalId)              // 改全局 activeTerminalId = A
  manager.getState()                      // 同步读
  await ensureRoot()                      // ← 挂起点
  manager.getState()                      // 若此刻 B 的 followTerminal 已把它改成 B → 读到 B
  readDirectory(path)                     // requireConnection() → 又是当前 active
```

`SftpManager.listDirectory/ensureRoot/changeToParentDirectory` 内部全部走 `requireConnection()` → `getActiveConnection()` → 单例 `activeTerminalId`（`SftpManager.ts:80,199-236,507-524`）。两个标签并发读目录时，谁后调 `followTerminal` 谁说了算。**这与「一标签一连接」的目标直接冲突。**

修法（二选一，推荐后者）：

| 方案 | 做法 | 评价 |
|---|---|---|
| L3-a | 在 `sftp.ts` 侧对 `followTerminal + 读` 加串行队列（互斥锁） | 最小改动，但把「跨标签并发」降级成「排队」，且仍依赖全局指针 |
| **L3-b（推荐）** | 给 `SftpManager` 增 `ensureRootOf(terminalId)` / `listDirectoryOf(terminalId, path)` / `changeToParentDirectoryOf(terminalId)`，直连 `this.connections.get(terminalId)`；`activeTerminalId` 降级为「VS Code 侧默认视图」的只读便利 | 消除竞态根因而非掩盖；VS Code 变体行为不变（仍走老方法） |

顺带修：`sftp.ts:186` 的 `refusal` 是**单槽**，并发打开连接时可能被别的操作消费。建议改为每次操作新建一个 verifier 闭包（把 refusal 变成局部变量），或按 `host:port` 键控。

客户端侧（可选但建议）：把 `sftpExpanded` / `sftpChildren` 一并提升到 `TabSession`，这样切标签回来时展开态与已读目录都还在。

验收：两标签同时进文件页 → 各自根目录正确、`rootPath` 不互换；对 A 点「上一级」不影响 B；`test/platform/dsh/sftp.test.ts` 加一条「两个 terminalId 并发 list」的用例。

#### L4（立项不动手）—— 宿主侧会话仓库

对齐官方：`session.create/attach/detach/list/close` RPC + 宿主 `Map<contentId, {...}>` + 有界屏幕快照 + hold 计数 + 空闲回收（参考 `unattendedTimeoutMs` 语义，**只在无 hold 时计时**）+ localStorage 绑定键 `at-terminal.binding.v1.*`。收益：刷新/重开窗口恢复会话。触发条件：用户明确要求「刷新不丢终端」时再做。

### 9.3 会话存活：`client/sessions.ts`（新文件）

会话对象（模块级 `Map<key, TerminalSession>`，key = `contentId`，无则退 `tab.id`，再无则常量）持有：
**socket / frames / flow / 有界输出环形缓冲 / 连接状态 / hostTerminalId / serverId / page**。

body 只做 **attach / detach**：
- 挂载：`attachEngine(session, engine)` —— 先把此前的输出按序**回放到新引擎**，回放用**真实的 acknowledge**（这些正是 host 因背压暂停的字节，确认它们才能让 host 继续）。
- 卸载（切走）：「只 detach，不 teardown」。

**什么活着、什么不活着**（如实记录）：

| | 后台标签 |
|---|---|
| WebSocket / PTY / 远端进程 | **活着** |
| 连接状态 / 目标服务器 / 当前页 | **活着**（`page` 也存会话里，切回来还在原页） |
| host 已发的输出 | **保留**在环形缓冲（上限 4 MiB / 20000 块，超限丢最旧并置 `truncated`，回放前先写 `ESC[0m ESC[2J ESC[3J ESC[H` 复位） |
| xterm 实例（屏幕缓冲、回滚、选区） | **没了**（engine 是 DOM 绑定的，随 body 销毁）——回放字节重建屏幕，只要环形缓冲还装得下整个会话就是逐字节等价 |

**背压策略刻意不改**：`flow` 仍然统计「已产出未渲染」字节，**即使没有引擎也照常计**。两个后果都是想要的：环形缓冲不会无界增长（越过 256 KiB 阈值 host 就暂停），**远端什么都没丢**（远端进程被写阻塞，而不是输出被丢弃）；切回来时回放把它们确认掉，host 恢复。代价写在明处：后台跑的长任务会在阈值处阻塞，直到用户回来看它。

**释放路径（三条，互为兜底）**：
1. `registerCloseHandler(KIND_SESSION, …)` —— 框架自身移除路径，且**在删除记录之前**调用（之后就没有 contentId 了）；
2. `tab.signal` abort —— **监听器注册在会话上而不是 body 的 cleanup 上**，因为 body 卸载正是关闭最可能发生的时刻，挂在 body 上的监听器会正好错过；
3. `openTabs` 清单收割 —— 盖住「压根不调 handler」的路径（pane 收起 / Session 被清 / 卸载）。带 `confirmedOpen` 守卫：**只收割自己曾经见过在清单里的会话**，因为清单启动时读的是已保存布局，一个尚未 adopt 的空快照会被误读成「所有标签都关了」而杀掉刚建的连接。

插件卸载 `ctx.effect(() => () => disposeAllSessions())`，否则 disable/enable 会留下没有标签、没有 chip、也够不着的 SSH 会话。

### 10.2 根因（bug 1）：`params` 的写入不保证在 body 首帧之前，而且首帧之后**不会**重渲染

| 事实 | 证据 |
|---|---|
| `params` 经 `place()` → `this.tabDomain.navigate(...)` 落到 occurrence 的 navigation | `dsh-client-ui-sidebar-right/lib/client.js:6478-6507`（`navigate` 在 `onCommitted` 回调里调用） |
| 同一次提交里，席位会先用 `params: void 0` 建 occurrence | 同文件 `:6089-6094`（`sync()` 的 `hold(sessionId, tab.id, { address, params: void 0, revision: 0 })`） |
| 两种顺序都可达 | `navigate` 对已存在的 occurrence 只做 `navigation.set(...)`（`:6123-6136`）；JSDoc 的「首帧已带 params」是对 **occurrence** 的说法，不是对「body 首帧可读」的保证 |
| **`params` 写入不会触发 body 重渲染** | `tabInfoFactory`（`:8965-9001`）：`useMemo` 依赖里放的是 navigation **句柄**（身份与标签同寿命），只有 `useStore(layout)` 会订阅 ⇒ 句柄内容变了不重渲染 |

上一轮的实现恰好是这种形态：`readTabParams(props)` 挂载时读一次 + `useRef` 一次性连接。
⇒ 一旦首帧读到的是空 params（`sync` 先跑），**此后永远读不到**，于是「双击 → 空标签 → 手动选」。

**日志给出的反证**（同一窗口）：两个会话标签的 `badge` 从未回到 `none`，也没有 `terminal.close` 痕迹；
`disposeSession` 会 `clearTabBadge`，而清空会唤醒所有已挂载 chip 重渲染（会有 `title … badge=none` 行）——
**该窗口内没有发生任何 dispose**。SSH 层 keepalive 也已确认真机开着（服务器配置 `keepAliveInterval: 30`，
`src/ssh/SshConnectionConfig.ts:85`，含跳板机那台）。所以**上一轮日志不足以判定**「切标签掐断 SSH」的具体路径，
本轮先做两件在不完全确定时也正确的事：

1. **不再让清单单独定生死**：`retainSessions` 只在「清单已不含该 contentId」**且**「occurrence signal 也已 abort
   （或该会话从未注册过 signal）」时释放。清单是**派生视图**（按会话 store 拼装，store 被重新 adopt 时会先发布一次空成员），
   拿那一刻当「所有标签都关了」正是「后台终端被本该保护它的订阅杀掉」这一形态的成因。
2. **abort 要与清单交叉验证**：`retainSessionSignal` 的 abort 若清单**仍列出**该标签，则**忽略并记一行日志**。
   真关闭不会因此漏掉：`sync()` 里 `inventory.update` 先跑、`tabDomain.sync`（abort）后跑，同一个 layout 提交里两者一致。
3. **补诊断**（下一轮可判定）：`dispose key=… why=close-handler|occurrence-abort|inventory-reap|unload|unspecified
   socket=… state=… target=…`、`ws-open`、`ws-close code=… clean=… reason=…`、`ws-error`、
   `inventory [keys]`、`inventory-drop-ignored`、`occurrence-abort-ignored`。

**代价写在明处**：若某个移除路径既不走 close handler、signal 又不 abort、清单也不再列出，会话会存活到插件卸载
（`disposeAllSessions('unload')`）。这是刻意选的：误杀用户正在用的 SSH 会话，比留下一个够不着的会话严重得多。

## 11. 落地记录（2026-10-08，第四轮）：切回标签后终端空白（会话活着、屏幕没了）

用户重启后反馈：**切换标签再切回来，SSH 显示已连接，但终端被清空了，连 `user@host` 都不显示；
按一下回车才出现。** 本轮据此取证、修复，并补上了这一整块此前**零覆盖**的门禁。

### 11.1 日志取证：SSH 没有断，丢的是屏幕

窗口 183 行（`06:58:44Z → 07:01:19Z`，即重启后的单次激活），全窗口统计：

| 找什么 | 结果 |
|---|---|
| `dispose key=… why=…` | **0 行** —— 四个释放路径一个都没走 ⇒ 会话没被我们释放 |
| `ws-close` / `ws-error` | **0 行** ⇒ WebSocket 没有掉 |
| 两个会话标签的 `badge` | 全程 `connected`（`06:58:50.556` 起）⇒ 状态层一切正常 |
| 每次切回来的 `session body mount` | 有（`06:58:55.161`、`58.183`、`59.811`…）⇒ body 确实随切换重新挂载 |
| `session body mount … params={}` + `target-adopted … source=seed` | 帧**仍未**把 params 交给 body，是 seed 兜底接住的（见 §11.5） |

用户那句"**按回车才显示**"本身就是判据：如果渲染端坏了（画布尺寸为 0、引擎挂在脱离文档的容器上），
回车产生的输出同样不会显示；它显示了，说明**渲染路径是好的、数据路径是空的**——新引擎手里没有可画的东西。

### 11.2 根因：三处叠加，都在 `sessions.ts`，且都属"留存策略"这一件事

| | 位置 | 缺陷 |
|---|---|---|
| **D1** | `consume()`（旧 `:663-680`） | 输出**只在 `session.engine === null` 时**才进环形缓冲。你在看着终端时的输出（连接横幅、`root@host:~#` 提示符、你敲的字与回显）全部直通 xterm、`return` 掉，**一个字都不留** |
| **D2** | `attachEngine()`（旧 `:833-847`） | 回放完就把环清空（`session.retained = []`）。于是**每次切走只回放"上一次挂载之后"的字节**，历史按访问次数递减 |
| **D3** | `teardown()`（旧 `:683-714`） | 也清空环 ⇒ 断线（或任何一次 teardown）同样把屏幕扔掉，与计划文档 UI-16 的"断线**保留屏幕**"相反 |

**D1 单独就足以产生所报告的症状**：xterm 实例随 body 卸载被 `dispose()`（`views/terminal.ts:93-97`），
屏幕只存在于这个实例里；环里只有"你离开期间到达的字节"，而**空闲 shell 在那一瞬间什么都不输出** ⇒
回放 0 字节 ⇒ 新引擎空白 ⇒ 回车让 shell 重新打印提示符 ⇒ 才出现。

### 11.3 为什么既有 1155 个测试一个都没看见

两个结构性盲区，都已在同轮修掉：

1. **bundle harness 永远造不出引擎**：`useRef` 的实现返回 `{current: null}`，且 shim 的 `createElement`
   不给 `props.ref` 赋值 ⇒ `TerminalView` 的建引擎 effect 因 ref 为空**提前 return** ⇒
   `session.engine` 在**所有**既有用例里恒为 `null` ⇒ `consume` 的"有引擎"分支是**不可达代码**，
   留存与否根本无从断言。
2. **`sessions.ts` 无法被直接 import**：`react` 是 external 且 `node_modules` 里不存在
   （只有 `@xterm`），单个 `import React from 'react'` 就让任何 node 侧测试加载失败。
   ⇒ 这个"切标签靠它活着"的模块**零直接测试**。
