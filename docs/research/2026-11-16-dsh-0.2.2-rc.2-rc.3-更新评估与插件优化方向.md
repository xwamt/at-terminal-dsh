> 取证方式：GitHub Releases API、`app.asar` 内 `@deepseek-ai/*` 包源码与 README、`npm run verify:dsh`、`npm test`、`npm run typecheck`、`npm run verify:kernel`  
> 前序评估：[`2026-11-09-dsh-0.2.2-rc.1-更新评估与插件优化方向.md`](./2026-11-09-dsh-0.2.2-rc.1-更新评估与插件优化方向.md)

## 0. 结论摘要

最新两个 DSH 发布是 **v0.2.2-rc.3（2026-11-13）** 和 **v0.2.2-rc.2（2026-11-11）**。rc.3 只有两项（DeepSeek 会话导入实验插件、Windows 应用内更新修复），对 AT Terminal **没有 API 影响**；真正有内容的是 rc.2：**Agent 终端可见化/用户接管、具名多层 SubAgent 与 AgentTeam、更多只读工具并行、插件动态注册 MCP、工具错误结构化、插件扩展聊天代码块、菜单定位与主题覆盖**。

本仓库当前实测状态：

| 检查 | 结果 |
|---|---|
| `npm run verify:dsh` | **12/12 通过**，19 个工具对 `dsh-tools` 0.2.2-rc.3 合约通过，设置 schema 对 schemastery 3.19.0 通过 |
| `npm test` | **101 个文件、1551 个用例中 2 个失败**：`test/docs/hostVersion.test.ts` 的 README badge 与 `dsh/README.md` 仍写 `0.2.2-rc.2`，实际安装是 `0.2.2-rc.3` |
| `npm run typecheck` | 通过（0 错误） |
| `npm run verify:kernel` | 4/4 通过 |

优先级建议：

1. **P0 版本声明收口**（XS）：把 README badge 和 `dsh/README.md` 的验证版本改到 rc.3；这是当前唯一红灯，且只是文档漂移，不动代码。
2. **P0 复核可选 SSH 终端的 rc.2 运行契约**（S）：DSH 0.2.2-rc.3 的 `TerminalSendOperation` 要求 `readOutput()`，插件的 `SshSendOperation` 只有 `consume()`；`terminal_send(run_in_background: true)` 的后台 job 读输出时会失败。先把接口补齐并做一次真实 smoke。
3. **P1 给只读工具加 `isConcurrencySafe`**（S–M）：DSH rc.2 的并行调度只认工具自己声明的 `isConcurrencySafe()`；本插件目前 19 个工具全部是默认的 `exclusive`，多文件读取仍是串行。收益直接、风险可控。
4. **P1 让 Agent 执行状态按 Agent/Session 分开**（M）：rc.2 的具名多层 SubAgent/AgentTeam 会让多个 Agent 同时调用远程命令；当前 `AgentExecutionBridge` 只有一个 `currentAction`，后一个会覆盖前一个，监控与审计会失真。
5. **P2 把可选 SSH 终端向“可见终端 + 用户接管”推进**（L，建议先做 spike）：这是 rc.2 最明显的产品级变化，也是本插件相对官方 `dsh-terminal-panel` 的体验缺口；但官方 panel 绑定 `ctx.terminalController` 的本地子进程，不能直接拿来跑 SSH，需要插件自己的面板通道。
6. **P2 小型安全/一致性项**：可选 SSH 终端拒绝 SubAgent 打开（官方 panel 已这样做）、限制每 Agent 的终端数、后台任务提示词适配 rc.2 的“完成通知自带小输出”。
7. **P2/P3 机会项**：用 `ctx.mcpManager.register()` 把 MCP bridge 从“手改 profile”变成插件生命周期注册；给 guard/pre-execute 的 deny 加结构化 `ToolErrorInfo`；按 rc.2 的 `conversation.chat.markdown.fence` 增加终端代码块 renderer；评估 `user_terminal_read` 对应的“读取用户 SSH 终端屏幕”能力。

### 2.3 当前设计边界

- Host half 不 import 任何 `@deepseek-ai/*`（`verify:kernel` 强制）；插件只能通过 `ctx` 服务、注入构造器或 vendoring 使用 DSH 能力。
- `ctx.fs` / `ctx.subprocess` 是单例，不能为了 SSH 去替换本地 provider。
- `dsh-client-ui-sidebar-documentpreview` 只接受 Session workspace 资源地址，远程 SFTP 没有对应 resourceAddress，不能直接复用其读取层。

- 远程 `apply_patch` 不进 DSH Review；这是产品事实，不是待办缺陷。

### P0-1 版本声明收口（XS）

**现状**：唯一红灯是 `README.md:6`、`dsh/README.md:9`、`dsh/README.md:651` 的 `0.2.2-rc.2`。`verify:dsh` 已经以 rc.3 跑通，说明不是兼容性问题。

**做法**：

1. `README.md:6` badge 改为 `DSH-0.2.2--rc.3_Verified`。
2. `dsh/README.md:9` 与 `:651` 改为 `0.2.2-rc.3`。
3. 可选：在 `verify:dsh` 的 manifest 检查里增加“`engines.dsh` 覆盖当前安装版本”的断言；目前 `>=0.2.2-rc.1 <0.3.0-0` 已覆盖 rc.3，但门禁不会主动提醒未来版本。
4. 运行 `npm test`，确认 101 文件 / 1551 用例全绿；这是后续所有改动的基线。

**收益**：恢复文档与真实安装一致；避免下一个版本继续在 rc.2/rc.3 之间漂移。  
**风险**：无。  
**工作量**：0.5 小时。

### P0-2 复核可选 SSH 终端的 rc.2 运行契约（S）

**现状（真实缺口）**：DSH 0.2.2-rc.3 的 `@deepseek-ai/dsh-terminal/src/types.ts:78-86` 要求 `TerminalSendOperation` 同时提供：

```ts
readOutput(): TerminalSendRead   // { delta: string; truncated: boolean }
cancel(): boolean
```

而 `@deepseek-ai/dsh-tool-terminal/src/background.ts` 的 `sendSource()` 在 `terminal_send(run_in_background: true)` 的后台 job 里直接调用 `live.readOutput()`。本插件 `src/platform/dsh/terminalBackend/sshBackend.ts:392-437` 的 `SshSendOperation` 只有 `consume()`（结算时用）和 `cancel(): void`，**没有 `readOutput()`**。结果是：前台 `terminal_send` 可能正常，但一旦用后台模式并由 `job_output` 收取，job 的输出源会因 `live.readOutput is not a function` 失败。`verify:dsh` 的第 12 项只校验组合形状，不执行 backend 方法，所以没有抓到。

**建议**：

1. `SshSendOperation` 增加独立读游标 `readOutput(): { delta, truncated }`，每次只返回自上次调用以来的新增输出（不能复用 `consume()`，否则会把结算时已有的输出重复返回）。
2. `cancel()` 改为返回 `boolean`：首次请求返回 `true`，已结算/重复调用返回 `false`，与 DSH 接口一致。
3. 在 `terminalEntry.ts` 的 `TerminalSpawnSpec` 中补 `owner`（见 P2-2），顺便让 backend 可在启动时检查 SubAgent。
4. 新增真实 smoke（不是 mock）：`terminal_open({type:'ssh', name:<server>})` → `terminal_send({run_in_background:true})` → 宿主 `job_output` 读到输出或看到 `[status: running]`；同时验证前台 `terminal_send` 的 `stdin_read` / `inferred_idle` 语义不变。
5. 在 `dsh/scripts/verify.mjs` 的 terminal bundle 检查里，静态断言 `terminal.bundle.js` 的 backend 暴露 `readOutput` / `cancel` 返回布尔值，或新增一个从 `dsh-terminal` 类型到实现的最小契约测试。

**收益**：修复可选 bundle 在 rc.2/rc.3 上的后台终端功能；避免“装了可选包，前台能用、后台任务报错”的半坏状态。  
**风险**：`readOutput` 是增量语义，必须正确维护游标；实现错会重复或丢失输出，需单测边界（空输出、截断、结算后再读）。  
**工作量**：0.5–1 天（含 smoke）。

### P1-1 给只读工具声明 `isConcurrencySafe`（S–M）

**依据**：DSH rc.2 的“更多只读工具可并行运行”不是对旧工具的自动优化。`dsh-tools/src/pipeline.ts:106-114` 写得很明确：

```ts
executionMode(exec) {
  const tool = this.resolveExecution(...)
  if (!tool?.isConcurrencySafe) return { kind: 'exclusive' }
  const concurrencySafe = tool.isConcurrencySafe(exec.arguments)
  return concurrencySafe === true ? { kind: 'parallel' } : { kind: 'exclusive' }
}
```

只有 `isConcurrencySafe(args) === true` 才会进入并行组；省略、抛错、返回非 `true` 全部按 `exclusive`。本仓库 `dsh/tools.js` 目前 **0 个** `isConcurrencySafe`，19 个工具都默认串行。

**建议范围**（只读且无共享消费状态）：

| 工具 | 理由 |
|---|---|
| `at_terminal_ping` | 不触达远端，只读本进程状态 |
| `at_terminal_list_ssh_servers` | 读配置与会话快照 |
| `at_terminal_get_terminal_context` | 读内存快照 |
| `at_terminal_sftp_list_directory` | SFTP 只读；`SftpSession.listDirectory` 内部已有并发 stat |
| `at_terminal_sftp_stat_path` | 单次 SFTP stat |
| `at_terminal_sftp_read_file` | 单次/分块 SFTP 读；底层 `SftpSession.readFile` 已有滑动窗口 |
| `at_terminal_get_hardware_metrics` | 固定只读探针；`HardwareMetricsCollector` 有短 TTL 缓存 |

**不要**声明并行的：`at_terminal_job_output`（读取会推进 job 的消费游标，两个并发读取会互相抢输出）、`at_terminal_run_remote_command`（会更新全局 `AgentExecutionBridge.currentAction`）、所有写类 SFTP 工具、`at_terminal_open_monitor`（有 UI 副作用）。

**实现要点**：

1. 在 `dsh/policy.js` 的 `TOOL_POLICY` 增加 `parallel: true` 标志（不要只按 `risk: 'read'` 推断，`job_output` 也是 `read` 但不可并行）。
2. `dsh/tools.js` 每个可并行工具定义加 `isConcurrencySafe: () => true`；`createTools()` 直接返回该字段，`ctx.tools.register()` 不会把它发给模型（`schemas()` 只投影 name/description/parameters）。
3. 在 `verify.mjs` 的 policy 检查里断言：`TOOL_POLICY[x].parallel === true` 当且仅当对应 definition 有 `isConcurrencySafe`；防止未来新增工具忘声明。
4. 增加一个并发测试：同一 `SftpAgentService` 上并发两个 `sftp_read_file`，断言两个结果完整、观察 map 不串；再测两个 `sftp_list_directory` 不同路径。

**收益**：模型一次请求多个远程文件时，实际执行从串行 RTT 变成并行；对高延迟链路收益最大。  
**风险**：SFTP 底层 `ssh2` 支持同连接多请求，但需要实测 `SftpSession` 的 `SFTP_PIPELINE_DEPTH` 与同一 `sftp` wrapper 并发打开多个读句柄的行为；先加测试再放开。  
**工作量**：0.5–1 天。

### P1-2 Agent 执行状态按 Agent/Session 分开（M）

**现状**：

- `src/agent/AgentExecutionBridge.ts:19-22` 只有一个 `currentAction`；`getSnapshot()`（`:127`）返回单个 `currentAction`。
- `src/agent/AgentToolService.ts:75` 的 `RunRemoteCommandInput` 没有 agent/session 字段；`recordActionStart`（`:195`）也不带 agent。
- `src/platform/dsh/client/models.ts:1094-1099` 的 `AgentExecutionSnapshot` 只有 `currentAction`、`recentAudits`、`activeTransfers`。
- `at_terminal_get_agent_execution_status` 的 output schema 也只有 `hasActiveAction` / `currentCommand` / `currentStatus`（`dsh/tools.js:1737` 起）。

**为什么 rc.2 让它变重要**：rc.2 的 SubAgent 支持具名、多层协作，AgentTeam 可以按 Session 开启；多个子 Agent 可以同时调用 `at_terminal_run_remote_command` 或 SFTP 工具。当前实现里后开始的命令会覆盖前一个的 `currentAction`，面板只会显示“最后一个动作”，审计里的 `sessionId` 虽然存在（`dsh/index.js:159`），但监控 UI 不展示，用户无法知道是哪个 Agent 在操作哪台机器。

**建议**：

1. `RunRemoteCommandInput` 增加 `agentId?: string`、`sessionId?: string`；`dsh/tools.js` 的 `createRunRemoteCommandTool.execute` 从 `exec.agent` 读取（`exec.agent?.id` 即 Session id，`exec.agent?.session?.id` 也可用），传入 service。
2. `AgentExecutionBridge` 把 `currentAction` 改为 `Map<string, AgentActionSnapshot>`（key 为 `agentId ?? 'default'`）；`getSnapshot()` 返回：
   - `currentAction`：保留旧字段，取“最近开始且仍在运行”的动作，兼容旧客户端；
   - `activeActions`：按开始时间排序的数组；
   - `recentAudits`：每条增加 `sessionId`、`serverId`、`tool`。
3. `AgentExecutionSnapshot` / `at_terminal_get_agent_execution_status` 增加 `activeActions` 数组（每项含 `agentId`、`sessionId`、`command`、`status`、`serverId`、`runningTimeMs`）；`monitorAgent.ts` 从单行改成列表，显示 Agent/Session 短标识。
4. `TransferProgressSnapshot` 也加可选 `agentId`，让并发上传能看出归属。

**收益**：Team 模式下监控不再“只见最后一个命令”；审计、用户判断和 `at_terminal_get_agent_execution_status` 的语义都能对上。  
**风险**：`AgentExecutionSnapshot` 是插件自己的客户端模型，不是 DSH 公共 API，改动可控；需要兼容旧字段避免 monitor 旧面板崩溃。  
**工作量**：1–2 天。

### P2-1 可选 SSH 终端：向“可见终端 + 用户接管”推进（L，建议先 spike）

**现状与依据**：

- DSH rc.2 的 `@deepseek-ai/dsh-terminal-panel` README 明确：它注册一个 `ctx.terminals` backend，把 `terminal_open` 的每个 Agent 会话变成**右侧栏可见 Tab**；用户第一次输入就接管，之后 `terminal_send` / `terminal_signal` 失败、`terminal_read` 仍可读，`terminal_close` 只移除 Agent 的列表而保留用户的 shell。
- 官方 `dsh-experimental-terminal-bundle/cordis.patch.yml` 已改成 `dsh-terminal` → `dsh-terminal-panel` → `dsh-tool-terminal` 三行。
- 本插件 `dsh-terminal-ssh/cordis.patch.yml:25-40` 仍是 `dsh-terminal` → 自己的 `ssh` backend → `dsh-tool-terminal`；`src/platform/dsh/terminalEntry.ts:197-207` 只 `terminals.registerBackend(...)`，没有向面板发布会话。
- `src/platform/dsh/terminalBackend/sshBackend.ts:149` 的 `sanitizeOutput()` 在 `feed()` 入口就剥掉 ANSI，注释说明“backend has no xterm renderer”；一旦要做可见终端，需要保留原始 ANSI 供 xterm 渲染，或至少增加 raw buffer，而模型读取仍用脱敏文本。

**不能做的事**：不要把 `dsh-terminal-panel` 直接挂到插件 bundle 上。它内部 `PanelTerminalBackend` 的 `open` 固定调用 `ctx.terminalController.openForAgent(agent, request, signal)`（`dsh-terminal-panel/src/index.ts`），而 `terminalController` 只负责本地 `ctx.subprocess.spawnTerminal`，没有 SSH provider seam；`backendType` 只是改变注册的 type 名，不会换执行环境。

**建议分两步**：

**Phase A（M，先做可观测性）**
- 在 `terminalEntry.ts` 维护一个 `Map<sessionId, {serverId, name, status, lastOutputAt}>`，通过 `globalThis` 弱引用或插件自己的 Host 服务向主 `dsh/index.js` 暴露只读 inventory；
- `at_terminal_get_terminal_context` 增加 `agentTerminals` 数组（`terminalId`、`serverId`、`name`、`status`、`lastOutputAt`），不暴露输出内容；
- 监控 HUD 的 Agent 页增加 “Agent terminals” 列表。

**Phase B（L，可见 Tab + 接管）**
- 在插件右侧栏新增 `type: 'at-terminal-agent'` 的 Tab：Host 端把 `ctx.terminals` 的 SSH session 包装成可 attach 的 terminal view（复用现有 xterm 引擎），用户输入通过 channel 写回 `SshPtySession`；
- 定义接管语义：用户第一次输入后，`terminal_send`/`terminal_signal` 拒绝、`terminal_read` 继续，`terminal_close` 只移除 Agent 归属（与官方 panel 一致）；
- `SshPtySession` 增加 raw ANSI ring（例如 256 KiB/4000 行）与 sanitized ring 两套视图；模型读 sanitized，面板读 raw；内存与清理策略写进 README。

**收益**：Agent 的 SSH 长任务（`tail -f`、部署、`psql`）用户可见、可接管；和 DSH 官方终端体验对齐，形成“远程 SSH 的官方级可见终端”。  
**风险**：这是跨 Host/Client/终端所有权的大改动；可能引入双输入源、会话泄漏、敏感输出进模型等问题，必须加开关（默认关闭）和权限边界。  
**工作量**：Phase A 约 1–2 天；Phase B 约 1–2 周。

### P2-2 可选 SSH 终端拒绝 SubAgent + 限制每 Agent 会话数（XS–S）

**依据**：官方 `dsh-terminal-panel` 在 `backend.ts` 中明确拒绝 SubAgent——`SUBAGENT_REFUSAL = 'Subagents cannot open terminals because the user cannot see them; use bash for shell commands instead.'`。它的理由是 SubAgent 的终端不会出现在用户正在看的 Session 里。

**现状**：本插件 `src/platform/dsh/terminalBackend/sshBackend.ts:99-105` 的本地 `TerminalSpawnSpec` 甚至没有 `owner` 字段；`createSshTerminalBackend.spawn`（`:494`）只校验 `name`，不检查 `spec.owner.session.header.origin`。rc.2 的多层 SubAgent 让这个缺口更容易被触发：子 Agent 可以开一个用户永远看不到的 SSH shell，直到 owner 销毁才释放。

**建议**：

1. 在 `TerminalSpawnSpec` 增加 `owner?: { session?: { header?: { origin?: string } } }`，`spawn` 中若 `origin === 'subagent'` 则拒绝，错误文案指向 `at_terminal_run_remote_command`（一次性命令）；
2. 若确实需要允许子 Agent，增加设置 `allowSubagentTerminals`（默认 `false`），并在 README 说明“不可见”风险；
3. 增加每 Agent 的会话上限（如 4，参考官方 `maxAgentTerminals` 默认 4），在 `terminalEntry.ts` 的 backend 外层计数；超过时明确报错，不静默阻塞。

**收益**：避免不可见长会话；与官方可见终端策略一致；限制资源滥用。  
**风险**：现有用户若依赖子 Agent 开 SSH 终端会受影响，默认拒绝需要在 README 写明理由和替代方案。  
**工作量**：0.5 天。

### P2-3 MCP bridge 改用 `ctx.mcpManager.register()`（S–M）

**依据**：rc.2 起插件可以动态注册 MCP 服务。`dsh-mcp-manager/README.md:84-104` 给出：

```ts
export const inject = ['mcpManager']
export function apply(ctx: Context): void {
  ctx.mcpManager.register('example', {
    transport: 'streamable-http',
    url: 'https://mcp.example.com/mcp',
    headers: { Authorization: 'Bearer ${credential:EXAMPLE_TOKEN}' },
  })
}
```

注册随插件生命周期卸载，不需要用户改 `cordis.patch.yml`。

**现状**：`dsh/README.md:303-341` 的 MCP bridge 仍靠 `npm run dsh:mcp:enable` 往 `~/.dsh/profiles/desktop/cordis.patch.yml` 追加 `dsh-mcp-client` 行；用户需要自己跑脚本、找 `AT_SERIES_HOST_APP`，升级/卸载时可能留下配置。

**建议**：

1. `dsh/index.js` 加可选 `ctx.inject(['mcpManager'], ...)`，配置新增 `enableMcpBridge`（默认 `false`）与 `mcpHubHostApp`（可选，留空则沿用 `enable-mcp.mjs` 的发现逻辑，读取 `~/.at-series/bridges` 最新心跳）。
2. 注册一个名为 `at-series-hub` 的 stdio entry，`command` 使用 DSH 托管 Node（参考 `enable-mcp.mjs`），`env` 带 `AT_SERIES_HOST_APP`；插件卸载自动移除。
3. 保留 `dsh/scripts/enable-mcp.mjs` 作为无 `mcpManager` 的旧宿主 fallback；README 说明两条路径不要同时启用。
4. 在设置页展示 `ctx.mcpManager.list()` 的状态（connected/error），替代只看 profile 文本。

**收益**：MCP bridge 从“手工 profile 维护”变成真正的插件设置；禁用/更新插件时自动清理。  
**风险**：`mcpManager` 不一定在所有组合中挂载；Hub 路径/凭据是环境相关，必须保持可选；与 `dsh-mcp-manager` 自身配置的 `servers` 命名冲突要检测。  
**工作量**：1 天左右。

### P2-4 结构化工具错误信息（S）

**依据**：DSH rc.2 强化了 `ToolErrorInfo`：`ToolGuardDenial` 和 `tools/pre-execute` 的 `deny` 可携带 `{ name, code, reason? }`，工具结果会持久化 `name`/`code`。`dsh-tools/src/pipeline.ts:689-692` 只对 `instanceof HarnessError` 的普通抛出提取 `info`，但 guard/pre-execute 的 `deny` 是显式字段，不要求类身份。

**现状**：`dsh/policy.js:132-157` 的 guard 只返回字符串；`createPreExecute` 的 `ask` 不携带结构化 code。插件审计的 `auditEntryFrom`（`dsh/index.js:124-171`）目前从 `result.error.info.reasonCode` 读原因，普通失败退化为 `runtime_error`。

**建议**：

1. 把 guard 的敏感路径拒绝改为：

```js
return {
  reason: '...',
  info: { name: 'AtTerminalPolicyError', code: 'AT_TERMINAL_SENSITIVE_PATH' }
}
```

2. `createPreExecute` 的 `ask` 前记录 `info: { name: 'AtTerminalPolicyError', code: 'AT_TERMINAL_APPROVAL_REQUIRED' }`（如果 `PreToolDecision` 的 `ask` 类型允许；不允许就只做 deny 路径）。
3. 审计读取 `result.error.info.code` 作为 `reasonCode` 的 fallback；保留现有小写 code 到新 `AT_TERMINAL_*` 的映射表，避免一次改太多字符串。
4. 不要为了普通工具体错误强行 `Object.setPrototypeOf` 冒充 `HarnessError`：`instanceof` 是跨包类身份，伪造会破坏后续版本的类型判断；普通 `Error` 继续用插件自己的 code 即可。

**收益**：UI/重试策略/统计可以按稳定 code 路由；审计不再只看到 `runtime_error`。  
**风险**：`ToolErrorInfo` 的 schema 是 DSH 版本相关，需用 `verify:dsh` 做契约验证；`ask` 带 `info` 的字段可能因版本不同被忽略，要有 fallback。  
**工作量**：0.5 天。

### P3-1 读取用户 SSH 终端屏幕（M，可选）

**依据**：`dsh-terminal-panel` 的 `readUserTerminals: true` 默认注册 `user_terminal_list` / `user_terminal_read`，让模型读取用户自己的终端屏幕；rc.2 明确“允许读取的用户终端内容会进入模型与会话记录”。

**现状**：本插件 `at_terminal_get_terminal_context` 的 description 写“active terminal context and recent history”，但实际返回只有 `focusedTerminal` / `connectedTerminals` 等元数据（`dsh/tools.js:461-521`），没有屏幕内容；`SshSession` 也不保留 Host 侧输出环。

**建议**：新增可选工具 `at_terminal_read_terminal`（或给 `get_terminal_context` 加 `includeOutput: true`），参数 `terminalId?`、`lines?`（默认 80，硬上限 500），读取 Host 侧为每个 UI 终端维护的有界 ring；默认 `readTerminalOutput: false`，开启时在设置页明确提示“终端内容可能含密钥/敏感信息，会进入模型上下文”。  
**收益**：Agent 可以回答“我屏幕上现在是什么/为什么你的命令卡住”，运维协作价值高。  
**风险**：隐私/敏感信息；Host 侧 ring 的内存成本；需要脱敏（复用 `redactSensitiveText`）和非常明确的 opt-in。  
**工作量**：1–2 天（含 ring 与测试）。

### P3-2 后台任务提示词适配 rc.2 通知（XS）

**现状**：`dsh/prompt.js:79` 说“A background command returns a job id: collect it with job_output...”。rc.2 起后台任务完成通知会直接携带小体积输出，并减少已读结果的重复通知。模型仍按旧提示会无条件多调一次 `job_output`。

**建议**：改为“完成通知若已带输出就不要重复读取；只有通知没有输出或需要增量时才调用 `job_output`，不要轮询”。同步 `dsh/skills.js` 的巡检技能措辞。  
**收益**：少一次工具调用、少一次结果 token；与宿主行为一致。  
**工作量**：0.2 天。

### P3-3 聊天代码块 / 菜单 / 主题的体验收口（各 S）

- **代码块**：rc.2 的 `conversation.chat.markdown.fence` 允许按语言渲染。可给 `ssh` / `console` / `log` 增加终端风格 renderer；但插件工具结果本来就是 `output.render` 文本，收益偏装饰，放在最后。
- **菜单定位**：`src/platform/dsh/client/menuFocus.ts` 的旧宿主 fallback 仍用自绘定位；在 80%/125% 缩放、平移、长列表下做一次真实面板走查，确认不需要新定位接口。新宿主路径已经走 `ctx.contextMenus`，不要回退。
- **主题**：插件使用 `--dsw-*` token；rc.2 改善自定义主题对通知、卡片、计划、任务的覆盖。可把 HUD 的 success/error 状态、monitor 卡片、settings tab 再过一遍亮/暗主题截图；不要引入字面颜色（`verify.mjs` 的 token bridge 检查已覆盖 `--vscode-*`，但 HUD 内联样式仍需人工看）。

## 4. 不建议做 / 不要踩的坑

| 不做 | 原因 |
|---|---|
| 直接把 `dsh-terminal-panel` 挂到 `dsh-terminal-ssh` | 它的 `PanelTerminalBackend` 固定调用 `ctx.terminalController.openForAgent`，只跑本地 `ctx.subprocess`，`backendType` 只改名字，不能把 SSH backend 接进去 |
| 替换 `ctx.subprocess` 把官方终端路由到 SSH | 一个组合只能有一个 subprocess provider，会与 `bash-local`/`pwsh-local` 冲突；正确路径仍是 `ctx.terminals.registerBackend` |
| 给 `at_terminal_job_output` 加 `isConcurrencySafe` | 它读取并推进 job 的消费游标；两个并发读取会互相抢输出，必须保持 exclusive |
| 直接 import `@deepseek-ai/dsh-error` | `link:` 安装的插件无法解析 app.asar 内的包；`verify.mjs` 也会把 `@deepseek-ai/*` 裸导入判为 FAIL。需要结构化错误时走 guard/pre-execute 的 `info` 字段，或像 schemastery 一样严格 vendor 并验证跨包身份 |
| 为了“Zod 版本一致”升级插件 zod | 插件把 zod 3 打进自己的 bundle，宿主 zod 4.6.6 是独立包；没有共享模块就没有冲突。只有未来把 schema 暴露给宿主或跨 bundle 共享时才需要统一 |
| 用 Session Projection 做实时监控 | Projection 是从已提交 Session 事件折叠出的读模型；插件的连接/传输/命令状态是实时内存状态，不是同一类数据（前序评估已结论，仍成立） |
| 把远程 `apply_patch` 当作 DSH Review | Review 只覆盖本地 `ctx.fs`；远程结果只能由插件自己的结果与审计呈现 |
| 默认读取用户终端输出 | `readUserTerminals` 类能力涉及密钥/敏感信息；必须是 opt-in + 脱敏 + 明确提示 |
| 同时安装官方 experimental terminal bundle 和本插件 optional SSH bundle 而不做冲突说明 | 两者都通过 `dsh-tool-terminal` 提供同名六工具（官方 panel 是本地 shell，插件是 SSH）。是否在 group scope 下发生重复注册尚未在本机实测，但用户很可能误以为两个终端互通；启用前必须验证，README 应明确“二选一/不要同时启用”，或在设置页检测并提示 |
