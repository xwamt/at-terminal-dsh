ctx.effect(() => ctx.locale.register(NS, { zh, en }), 'at-terminal: dictionaries');

- **契约**：`main.ts:35-38` 声明 `{ bind(ns): Translate; register(ns, dicts: {zh, en}): () => void }`
- **生命周期**：包在 `ctx.effect` 里，卸载即随 disposer 移除
- **组件侧**：`body.ts:77-84` `wrapWithLocale` 用 `BodyLocale.Provider` 下发 `t`，`AtTerminalTitle`（`body.ts:88`）经 `useContext` 取用
- **另一套**：`dsh/locale/{en,zh-CN}.json` 是**插件管理器卡片**文案（`meta.title` / `meta.description`），与面板字典是两套，按 `i18n.ts:2-3` 注释所述分工

测试侧：`test/dsh/client-bundle.test.ts:663-670` 断言注册了恰好 1 个命名空间且为 `atTerminal`。**（该测试只抽查 `mode.assets` 一个键，不校验全键集——见缺口 4。）**

#### 2.4 U4 新增文案的 key 复用 [实测]

| key | zh | en | 语义是否匹配 |
|---|---|---|---|
| `terminal.reconnect` | 重连 | Reconnect | ⚠️ 见下 |
| `mode.terminal` | 终端 | Terminal | ✅ 匹配 |

**`mode.terminal`**：用在 SFTP 空态的「去终端页」按钮（`sftp.ts:431`）。`sftp.ts:409-413` 注释说明理由——按钮与它要跳过去的那个 tab 用同一个名字，避免给同一目的地起两个名。**双语齐备，语义匹配。**

**`terminal.reconnect`**：**双语齐备，但语义有偏差。** 它用在 `sftp.ts:473` 的「重连」按钮上，而该按钮的 `onClick` 实际是 `props.onRefresh`（`sftp.ts:470`）——**它不重连，只是重新读一次目录**。`sftp.ts:443-450` 的注释诚实登记了这一点：插件没有从 SFTP 页重连会话的 RPC，重连归终端页所有。

代码注释是诚实的，但**用户看到的标签承诺了「重连」而点击得到的是「重试读取」**。若会话确已断开，重读大概率仍失败。这是**文案与行为的落差**，属产品决策，我如实登记而不擅自改。`sftp.disconnected` 文案本身（zh: 「重新连接后才能继续展开」/ en: 「expanding again needs a reconnection」）与实际行为也是同一落差。

### 残留缺口（DSH-43）

1. **`terminal.reconnect` 标签承诺「重连」但行为是 `onRefresh` 重读** — `sftp.ts:470-473`。代码注释已诚实登记，标签本身未改。
2. **`body.heading`、`summary.title`、`servers.connect/edit/remove`、`menu.*` 等约 60 个键静态扫描看似孤儿** — [实测]复核后确认**绝大多数经动态键调用**（`errorKey` `models.ts:97-121` 19 个码、`sftpDirFailureKey` `models.ts:138-145` 4 个变体、`labelKey`/`titleKey`/`copyKey`/`trustHelpKey`/`hintKey`/`modeLabelKey` 等），例如 `terminal.pick` 由 `body.ts:483` 动态调用。**非缺陷，仅记录我的静态扫描方法会产生假阳性。**
3. **运行时 locale 切换能否触发面板重渲染，未能静态证明** [推断] — 面板用 `BodyLocale.Provider` 传 `t`，但 `grep subscribe|onChange|useSyncExternalStore|addEventListener` 在 `body.ts` / `main.ts` **零命中**。`wrapWithLocale` 在注册时捕获 `t` 并包成组件。**这是否会在宿主切语言时重渲染，取决于宿主是否重挂载 slot —— 属于 Harness 侧行为，本仓库无法证。** 建议真机切一次中英确认。
4. **无全键集一致性测试** — 188 键的完整性靠本次人工脚本验证，`client-bundle.test.ts:668-669` 只抽查 1 个键。计划第 714 行称「键集一致性由 client-models 断言」，但我在 `test/dsh/client-models.test.ts` 中**未搜到该断言**（`grep -n "i18n|locale|zh" ` 零命中）。**可能断言已被移除或从未落地，建议收口时确认。**

#### 情形一：无终端 [实测]

- **渲染位置**：`views/sftp.ts:414-435`（`listing.kind === 'none'`）
- **类别**：**树外状态**（`renderStatus` 内，`.att-hint`），**不走** `renderFailure`
- **文案 key**：`sftp.noTerminal`
  - zh：「没有活动的 SSH 终端。文件树跟随当前终端——先到「终端」页连接一台服务器。」
  - en：「No active SSH terminal. The file tree follows the current terminal — connect a server on the Terminal page first.」
- **出路**：✅ **有**。按钮 `sftp.ts:422-432`，`data-at-terminal-action="sftp-goto-terminal"`，`onClick: () => props.onMode('terminal')` —— 复用页面自带 nav 回调，跳终端页。标签 `mode.terminal`。

同语义的页面级失败另有一码：`error.noActiveTerminal`（`models.ts:114`），走 `renderFailure`，`zh` = 「没有已连接的 SSH 终端。先到「终端」页连接一台服务器，文件树会跟随该终端。」

#### 情形二：SFTP 失败 [实测] —— **两类都要分清**

**（a）树内行级失败（U3 改的）**

- **渲染位置**：`views/sftp.ts:302-340`（`row.kind === 'failed'`）
- **类别**：**行级**，明确**不**用 `renderFailure` —— `sftp.ts:289-291` 注释说明理由：Host 的原始消息（`No such file or directory: /root/x`）会报出用户没问的路径且无可执行动作
- **文案 key**：`sftpDirFailureKey(code)`（`models.ts:138-145`）**按码分 4 层**：
  | 码 | key | zh |
  |---|---|---|
  | `sftp-no-such-file` | `sftp.dirFailedNoSuchFile` | 这一层没有读到：远端已不存在该路径，可能刚被删除或改名。 |
  | `sftp-permission-denied` | `sftp.dirFailedPermissionDenied` | 这一层没有读到：当前登录账号没有读取它的权限。 |
  | `sftp-read-failed` | `sftp.dirFailedReadFailed` | 这一层没有读到：读取时出了错，可以重试。 |
  | 其它 | `sftp.dirFailed` | 这一层没有读到内容。 |

  **四个变体双语齐备。** 未知码兜底到 `sftp.dirFailed` 而非静默——`models.ts:142-144` 注释说这是为了避免树里出现看似「空」的静默缺口。
- **出路**：✅ **有**。真实 `<button>`（`sftp.ts:325-339`），`data-at-terminal-action="sftp-retry-dir"`，`onClick: props.onRefresh`，标签 `sftp.retry`（zh「重试」/ en「Retry」）。`sftp.ts:297-301` 注释点明为何必须是真按钮：行本身不是 tab 停靠点（`sftpRowFocusable` 有意排除读取态），行内无控件则键盘用户无法重试。
- **原始错误码保留**：`title: code`（`sftp.ts:310`）+ `data-at-terminal-sftp-code`（:312）
- **已知限制**（代码自述，`sftp.ts:320-324`）：重试是重读整棵树，非本层——因页面无 per-path 重读 props；且失败子节点被 body 缓存，收起再展开不会消失

**（b）页面级失败**

- **渲染位置**：`views/sftp.ts:388-393`（`state.kind === 'failed'`）→ `renderFailure`
- **类别**：**页面级**，`att-banner`，三段式（`shared.ts:36-44`）：`error.title` + `t(errorKey(code))` + `error.detail` 带原始码与消息
- **文案 key**：`error.sftpReadFailed` / `sftpNoSuchFile` / `sftpPermissionDenied` / `sftpDisconnected`（`models.ts:116-120`），双语齐备
- **出路**：⚠️ **无内嵌操作按钮**。`renderFailure`（`shared.ts:36-44`）只渲染三段文字，**没有 actions 容器**（对比 `att-banner .att-banner-actions`，`styles.ts:503` 是有的，但 `renderFailure` 不用它）。出路是工具栏刷新（`sftp.ts:520-526`）。
- **设计正确**：`sftp.ts:389-391` 注释强调失败的读**绝不渲染成空树**——`sftp-disconnected` 与 `no-active-terminal` 含义不同，静默空列表会同时掩盖两者。这是 §0.19.7 回归的修正方向。

#### 情形三：无服务器 [实测]

- **渲染位置**：`views/assets.ts:197-200`（`servers.length === 0`）
- **类别**：**树外/列表外状态**（`renderList` 内，`.att-hint`），不走 `renderFailure`
- **文案 key**：`servers.empty`
  - zh：「还没有服务器。点「新增服务器」创建，或从 VS Code 变体「导入」资产包。」
  - en：「No servers yet. Create one with "New Server", or import an asset package from the VS Code variant.」
- **出路**：⚠️ **文案内嵌了出路，但无内嵌按钮**。文案点名「新增服务器」和「导入」，二者都在工具栏（`assets.ts:269-270`，`toolbar.new` / `toolbar.import`）。**文案与出路一致，只是按钮在工具栏而非空态里。**
  - 对比：U4 给 SFTP 空态补了内嵌按钮（`sftp.ts:419-433`），**资产页空态没补**。两者不一致。
- 附带：目录为空（`sftp.empty`）走 `sftp.ts:480-484`，**无按钮**（无需出路，目录本身没坏）

### 残留缺口（DSH-24）

### P0 修法更正 —— 原文的建议不可用

本报告原建议前景改 `--dsw-alias-label-primary`。**那条是错的**：实测发现 `--dsw-alias-label-primary` 与 `--dsw-alias-brand-primary` 在**两个主题里都是同一个 token**（浅色都解到 `neutral-bluish-1000`、暗色都解到 `neutral-bluish-50`），所以拿它当前景等于背景本身，对比度 **1.00:1**，比原来的 1.05:1 更糟。

试错过程留档，避免重复：

| 候选前景 | 浅色 | 暗色 | 结论 |
|---|---|---|---|

依据是官方 `Button.module.css` 的 `.primary` 本身就成对使用
`background: var(--dsw-alias-button-primary-fill)` + `color: var(--dsw-alias-label-primary-foreground)` —— 这个 token 就是为「primary 填充上的前景」而设的。

### 为什么这个缺陷能活过四轮评审
