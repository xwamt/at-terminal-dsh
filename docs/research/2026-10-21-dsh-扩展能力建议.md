# AT Terminal (DSH) 可扩展能力建议

> 评审对象：`at-terminal-dsh` `main` @ `37067b7`（0.2.0），安装态 `link:` 到本机 profile `desktop`。
> 接口取证：本机 DeepSeek Harness Desktop **`0.2.1-rc.2`**（`app.asar` 内 307 个 `@deepseek-ai/*` 包，含 cordis/schemastery 等框架包；组合按 `dsh-base` → `dsh-web-app` → `dsh-web-app/presets/*` → profile patch 四层叠加）。
> 原则：只建议**真实存在且已挂载**的接口；每条给出落点文件、收益、约束与验收口径。与产品边界冲突的项进第 6 节「不做清单」。
> 落地计划：[`docs/plans/2026-10-21-dsh-语义接缝补齐与一致性收口任务计划.md`](../plans/2026-10-21-dsh-语义接缝补齐与一致性收口任务计划.md)（把本文 14 项拆成 6 个切片、17 个任务，含门禁插入点与反向测试做法）。

---

## 0. 结论摘要

插件当前把 DSH 用成了**两条通道 + 三种 UI 席位**：`ctx.tools`（15 个工具）+ `ctx.webServer`（自建 HTTP/SSE/WS 载体），UI 侧只有 `sidebarRightTabs` / `slots` / `shortcuts` / `locale`。这套东西能跑，但**DSH 0.2 里与本插件定位强相关的 6 个接口一个都没用**：`ctx.systemPrompt`、`ctx.commands`、`ctx.tools.guard()`/`tools/pre-execute`、`tools/result`、`ctx.jobs`、`ctx.sessionProjections`。

| 判断 | 结论 |
|---|---|
| 定位是否准确 | 是。远程 SSH 终端 + 资产/主机信任 + Agent 运维直连，与官方 `dsh-terminal`（本地 shell）不重叠，与 `dsh-ssh`（**未随包发布**，`app.asar` 内 0 命中）也不冲突。 |
| 最大的浪费 | 自建 HTTP 载体承担了 Typert Remote 的职责，却没有继承后者的 Host/Origin 围栏、取消与流重连语义；而真正该用的**语义层**（提示词、命令、护栏、审计、后台任务）全部空缺。 |
| 最大的风险 | 授权与审计写在工具内部（`AgentToolService` → `SftpWriteAuthorizer`），任何新工具或直接调服务都绕过它们；计划里的 `tools/pre-execute` + `guard()` 硬红线（DSH-35/36）仍是待办。 |
| 最值得先做的 3 件事 | ① `tools/result` 观察者 + 真正的 JSONL 审计（现有 `AgentAuditLog` 是死代码）；② `ctx.jobs` 承载长任务；③ `ctx.systemPrompt` 段替换「把用法塞进 description」的 ~2.4k token 常驻开销。 |
| 最容易被忽略的一致性问题 | `open_monitor` 恒返回 `opened: true`；`get_hardware_metrics` 绕过命令策略直接跑远端脚本；README 宣称的三档写授权在 DSH 侧只剩 `once`；`docs/features*.md` 对「full trust 是否跳过敏感路径确认」自相矛盾；README 工具表列了不存在的 `sftp_copy`、漏了 4 个已注册工具；两个设置项在 dsh 侧无人消费。 |

## 2. A 组：Agent 面（提示词 / 命令 / 护栏 / 审计）

### R1 用 `ctx.systemPrompt.section()` 承载运维准则，别塞进 15 个 description

- **接口**：`ctx.systemPrompt.section({ name, order, text })`；`ctx.systemPrompt.variable(name, provider)` 供动态事实（当前信任档、可用服务器数）。
- **证据**：`dsh-tools` README 明确「`defineTool()`、注册表模式投影和系统提示组装会保留 `deferLoading`」，同时段注册是**每次组装按 order 拼接**的独立段；`dsh-base:505` 已挂载。
- **现状问题**（本次实测拆分，§0.6 口径）：description 合计 1 963 B、参数 schema 合计 4 785 B。真正超标的是**跨工具重复**与**参数里塞说明**：
  - `at_terminal_ping` 的 description 320 字符，`list_ssh_servers` 186、`get_terminal_context` 114 —— 前者的「何时该调用、能读到什么」在段里说一次即可；
  - `open_monitor` 的参数 schema 578 B（全表最大），而它只有 3 个可选参数：`target` 的 enum description 用一整句解释两个取值，`mode` 又用一整句解释 `float`/`hud`，而工具 description 已经点过「hardware / agent_execution」；
  - 同一个「trust 三级」语义分散在 `list_ssh_servers`（`agentCommandTrust`/`agentCommandAutoApprove`）与 `run_remote_command`（「evaluated against the server trust level」）两处。
  `skills/agent-experience` 自己写着「Say each fact once」「Put parameter rules on the parameter」——当前实现两条都违反了。
- **做法**：新增 `dsh/prompt.js`，注册 1 个段（order ≈ 100，与 `tool:*` 同带）：
  - 段内只写「三类工具的能力边界 + 三档 trust 的差异 + 改远端文件的推荐顺序（stat → read → write with overwrite）」；
  - 动态事实走 `variable('at_terminal_trust', …)`，读 `readSettings(config)` 与已连接服务器摘要；
  - 各工具 description 压到「做什么、返回什么」一句，参数规则回落到参数 description。
- **收益**：预计工具定义体积从 7 811 B 降到 ≤5 400 B（−31%，主要来自搬进提示词段的「怎么用」叙述与重复的 enum 说明），且准则**只出现一次**；改准则不再动 15 个文件。**注意**：真正的参数说明要保留（`agent-experience` 要求「Put parameter rules on the parameter」），砍的是跨工具重复与「工具怎么用」的叙述。
- **约束/验收**：`name` 必须与既有贡献不撞（如 `tool:at-terminal`）；段文本不得引用未注册的 `{{var}}`，否则组装失败（`dsh-system-prompt` 明确会 fail）。验收：`ping` 前后首轮 prompt 字节数对比 + `cordis_inspect_query` 读组装结果。

### R2 把 `skills/` 里的运维技能注册成运行时 skill（`ctx.skills.register`）

- **接口**：`ctx.skills.register({ name, description, whenToUse?, content, invocation? })`；注册表在 host plane（`dsh-base:308`），`skill-filesystem` 在 web 侧被 preset 接管不影响全局层。
- **现状**：仓库根 `skills/`（`agent-experience`、`writing-ops-documents` 等）只服务于「开发本插件的人」，运行时模型完全看不见；巡检/排障/变更记录这些**正是 Agent 调这些工具时需要的操作规程**。
- **做法**：注册 2~3 个技能（`at-terminal-inspection`、`at-terminal-remote-edit`、`at-terminal-incident-log`），正文复用 `skills/writing-ops-documents` 的模板骨架；`invocation: { modelInvocable: true, userInvocable: true }`。
- **收益**：按需加载（省常驻 token）+ 可被 `/` 菜单与 `skill` 工具发现；R1 的段里只需留一句「需要巡检/变更记录流程时加载 `at-terminal-*` 技能」。
- **约束/验收**：`name` 必须 kebab-case 且全局唯一，重复注册会**告警并忽略**（`skill-lib.js:198`）——把「是否真的注册上」写成 verify 项，别靠日志。

### R3 把授权红线迁到 `ctx.tools.guard()` + `tools/pre-execute`（落地计划里的 DSH-35/36）

- **接口**：
  - `ctx.tools.guard(fn)`：**同步**、单调、不可被后续 `allow` 翻盘；返回字符串即 deny（`tools-lib.js:3017`）。
  - `tools/pre-execute` waterfall：可返回 `{ kind:'ask', reason, displayReason }`，由 registry 走 `ctx.approval.request()`，`allowed-once` 才放行。
- **现状**：授权在 `AgentToolService.runRemoteCommand()` 内部（先 `authorizeRemoteCommand` 再 `confirmation.confirmCommand`）。任何绕过该类的入口——`HardwareMetricsCollector`（R14-②）、未来的 SFTP 批量工具、或直接把 `SftpAgentService` 暴露出去——**完全不受约束**。
- **做法**：
  - `guard` 负责**不可撤销**项：`at_terminal_sftp_delete` 在敏感路径（`~/.ssh`、`/etc`、`*.service`、`authorized_keys`、`sudoers*`、`crontab`）上无条件 deny（真正的「清一次要确认两次」不适合既有 `once` 语义，交给 guard 直接拒）。
  - `pre-execute` 负责**可协商**项：按 `serverId` 的 trust 档算 allow/ask，把 `displayReason` 留成现有 `formatRemoteCommandConfirmMessage()` 的输出——**弹窗文案一行不用改**。
  - 工具内部保留「二次校验」不必删；guard 是**外层**护栏，不替代内部作者者。
- **收益**：新增工具自动继承护栏；`verify.mjs` 可加一项「每个 `at_terminal_*` 工具都在 guard 覆盖表里」的静态检查。
- **约束/验收**：guard 是同步的，**不能**在里面问用户；`pre-execute` 不能改写 `exec.arguments`（README 明确设计如此）。验收：对一个 `agentCommandTrust: 'none'` 的服务器直接调服务（不经工具）仍被拦——即护栏在 registry 层而非工具层。

### R4 `tools/result` 观察者 + 真实审计落盘（DSH-39，修死代码）

- **接口**：`ctx.on('tools/result', (exec, result) => …)`（emit 语义，观察者异常只记日志、不影响结果，`tools-lib.js:3509`/`:3513`）。
- **现状（严重）**：`src/agent/AgentAuditLog.ts` 有完整实现（redact + JSONL + 串行 append），但 `createDshAgentToolService` **没有构造它**，`entry.ts` 未导出，`host.bundle.js` 里 `agent-audit.jsonl` **0 命中**。所以：
  - 落盘审计 = 不存在；
  - 「历史执行」只来自内存 `AgentExecutionBridge.recentAudits`（上限 50 条，`AgentExecutionBridge.ts:28`），刷新页面/重启即丢；
  - 计划文档里「审计记下策略决策（reasonCode/action/trust）」在 DSH 侧未生效。
- **做法**：在 `dsh/index.js` 的 `ctx.effect` 里注册 `tools/result` 观察者，只处理 `name.startsWith('at_terminal_')`：把 `exec.arguments`（脱敏后）+ `result.isError` + `exec.agent.session` id 写 `AgentAuditLog`（`storageDir` 用 `storageDir()`，与导入私钥同目录策略）。
- **收益**：审计从「UI 内存」变成「宿主文件 + 会话事件」；`get_agent_execution_status` 的 `recentAudits` 可改为读审计尾部而非内存环。
- **约束/验收**：观察者必须 `try/catch` 且不阻塞（dispatch 已隔离异常，但仍不要 await I/O 到结果路径上——用队列）。验收：一次 `run_remote_command` 后 `<DSH_HOME>/at-terminal/agent-audit.jsonl` 出现一行且命令已脱敏。

## 3. B 组：执行面（长任务 / 持久会话 / 大结果 / 超时）

### R5 长任务交给 `ctx.jobs`（大传输、批量巡检、日志跟踪）

- **接口**：`ctx.jobs.start({ owner, kind, label, run(handle), output?, outputLimitBytes? })`，`handle.append/updateProgress`；模型侧用 `job_output/job_list/job_kill` 收集（`dsh-tool-jobs` 会挂 controller，`standard` preset 已挂）。
- **现状**：所有工具都是**同步等待**：
  - `run_remote_command` 默认 30 s、上限 120 s（`RemoteCommandExecutor.ts:36-37`），超时只 `stream.close()`（`RemoteCommandExecutor.ts:115-119`）——远端进程仍在跑，模型重试即**双执行**；
  - SFTP 读无超时（`SftpAgentService.ts:145-177` 整段没有 `withTimeout`，只有写/删有 60 s）；
  - 大目录 `list_directory`、大文件读都靠一次调用硬扛。
- **做法**：给 `run_remote_command` 增加 `run_in_background` 语义（当 `timeoutMs` 超过 30 s 或用户显式要求时）：
  - `ctx.jobs.start()` 里包一个 executor 循环，`:append` 增量 stdout/stderr；
  - 返回 `{ kind: 'background', jobId }`（**结构化 handle，不解析人类文案**，这是计划 DSH-38 的原话）；
  - 前台路径不变，保持 15 个工具的名字/参数兼容。
- **收益**：`apt-get upgrade`、`tail -f`、`rsync` 这类真实运维动作第一次变得可用；超时不再等于「进程还在跑但 Agent 以为失败」。
- **约束/验收**：`jobs.start()` 在没有 controller 的组合里会抛「no job controller serves this agent」——必须 catch 并**降级为前台**（preset 可关 `tool-jobs`）。验收：后台跑 `sleep 60` 后 `job_kill` 能真正终止远端进程（用 pidfile 校验）。

### R6 用 `ctx.terminals.registerBackend()` 给 Agent 一条**持久 SSH 会话**（推荐，但需自建 bundle）

- **接口**：`ctx.terminals.registerBackend({ type, spawn, read, send, signal, close, status })`；消费方是官方 6 个 `terminal_*` 工具（`terminal_open/send/read/signal/close/list`），带 owner 隔离（`FOREIGN_SESSION`）与 `run_in_background` job 集成。
- **现状**：`run_remote_command` 是**一次性 exec**：没有 `cd` 延续、没有 `sudo` 交互、没有 REPL。用户侧有 xterm 全屏终端，Agent 侧却是行式一次性命令——这是当前能力面最大的不对称。
- **做法**：
  1. 新 bundle（或本 bundle 的 patch 追加行）：`cordis:group` + `isolate: { terminals: true }`，内含 `dsh-terminal`（注册表）、本插件的 `ssh` backend、`dsh-tool-terminal`；照抄 `dsh-experimental-terminal-bundle/cordis.patch.yml` 的结构（这是官方给「opt-in 持久终端」的现成范式）。
  2. backend `type: 'ssh'`，`spawn(spec)` 复用 `createDshTerminalApi(...).open()`；`owner` 由 registry 给，`cwd` 走 `ctx.workingDirectory`。
  3. `send` 的 ready 判定（`stdin_read` / `inferred_idle` / `timeout`）直接映射现有 `SshSession` 输出流，**不要**自己发明等待语义。
- **收益**：Agent 获得 `terminal_send(run_in_background:true)` + `job_kill` 的真 `SIGINT`；`sudo`、`top`、`psql` 一类交互第一次进入 Agent 能力面。
- **约束/验收**：web 组合**默认不挂 `ctx.terminals`**（只有 `dsh-sdk-minimal` 有行），所以必须由本插件插入这 3 行；`api-terminal-controller`（右侧栏本地终端）**不消费** `ctx.terminals`，所以这条**不会**替换现有 UI——纯增量。验收：`terminal_open({type:'ssh'})` 后 `terminal_send` 连续两次 `cd` 生效；owner A 无法访问 owner B 的 session id。

### R7 大结果落 `ctx.spillStore`，别把 256 KB 当上限

- **接口**：`ctx.spillStore.saveText({ owner: { sessionId }, suggestedName, content })` → `{ locator, bytes, retrievalHint }`；`dsh-spill-policy` 已按 12 500 token 预算做「首尾保留 + 完整文件路径」替换。
- **现状**：`run_remote_command` 的 `maxOutputBytes` 硬顶 256 000（`RemoteCommandExecutor.ts:38-39`），超了**直接截断丢弃**；`sftp_read_file` 硬顶 256 KiB（`MAX_READ_BYTES`，`SftpAgentService.ts:81`）。模型只能看到「truncated: true」，没有取回路径。
- **做法**：工具在执行体里判断「原文超预算」→ `saveText` → 输出 `content` 保留首尾 + `spillPath`；`output.render` 里把它渲染成可点击路径。审计只记 locator，不记原文。
- **收益**：`journalctl -u x --no-pager | tail -2000`、`docker logs` 这类场景从「看不到」变成「可 grep 可续读」；与 `skills/agent-experience` 的「Prefer bounded outputs / provide a way to retrieve more」直接对齐。
- **约束/验收**：`spillStore` 只有 local 实现且按 session 隔离——工具必须拿得到 `exec.agent.session`；无 agent 的调用要降级为截断（不要抛）。验收：一次 1 MB 输出后 `locator` 可被 `read`/`grep` 打开。

### R8 声明 `timeoutMs`，并给读路径补超时

- **接口**：工具定义支持 `timeoutMs`（`tools.register()` 校验为正有限数），由 `@deepseek-ai/dsh-tool-call-timeout-policy`（`dsh-base:408` 已挂）**真正执行**并映射为 `TOOL_TIMEOUT`。
- **现状**：`dsh/tools.js` 里 `timeoutMs` 只作为 `run_remote_command` 的**参数**出现（:383），没有任何工具**声明**定义级超时；读/列目录路径完全没有 `withTimeout`。
- **做法**：给 `sftp_read_file` / `sftp_list_directory` / `sftp_stat_path` / `get_hardware_metrics` 声明 `timeoutMs`（例如 20 s / 30 s / 10 s / 8 s），并在 `SftpAgentService` 的读路径包 `withTimeout`（复用 `WRITE_TIMEOUT_MS` 的写法）。**注意**：`timeoutMs` 只是声明，靠 policy 生效——所以要在 `ping` 的 `capabilities` 里如实体现「超时由宿主策略执行」。
- **收益**：SFTP 读卡在 60 s+ 的挂起从「工具看似正常返回空」变成模型可识别的 `TOOL_TIMEOUT`。

## 4. C 组：交互面（命令 / 选择器 / 设置面板 / 启动体积）

### R9 `/ssh` 命令族：`ctx.commands`(Host) + `ctx.commandUi`(Client)

- **接口**：
  - Host：`ctx.commands.register({ name, description, input?, handler })`，**直连 agent、不产生模型消息**（`dsh-commands` README 首段），结果写 `command/run`/`command/done` 事件。
  - Client：`ctx.commandUi` 的 `popupSelect` / `action`，可装饰既有宿主命令；`ui-commands` 在 web 组合已挂（`dsh-web-app:374`）。
- **现状**：日常操作（连哪台、看硬件、开监控）只能**通过对话让模型调工具**——每次都花 token、每次都进 transcript，而 `/model`、`/permission` 这类可以直接触发。
- **做法**：
  - `/ssh-server`（popupSelect：已配置服务器 + 连接状态）→ 开终端 tab；
  - `/ssh-metrics [serverId]`（action）→ 直接调 `monitor.metrics.get` 并把 HUD 打开；
  - `/ssh-audit`（action）→ 打开执行历史；
  - `/ssh-trust`（popupSelect：待信任指纹）→ 复用 `terminal.trustHost`。
- **收益**：把「能力发现」从模型侧移到命令面板；`/ssh-*` 行在 `/` 菜单里就是插件的能力目录。与 R1 配合可再压缩提示词。
- **约束/验收**：同一作用域内重名会抛；命令语法严格（第 0 字节必须是 `/`）。验收：`/ssh-metrics` 不产生模型消息（会话日志只有 `command/*` 事件），且 HUD 真的打开。

### R10 用 `ctx.userQuestions.ask()` 恢复三档写授权，并给「多服务器」一个选择器

- **接口**：`ctx.userQuestions.ask({ questions: [{ id, question, detail?, options: [{label, description?}] }], agent, signal })` → 选定项；只允许 **root agent**（`DELEGATED_CALLER` 会拒）。
- **现状（文档-实现漂移）**：`SftpWriteAuthorizer.resolveAllowedScopes()` 仍然算 `['once','directory','session']`（15 分钟 / 本会话），`docs/features.md:77` 与 `docs/features.zh-CN.md:80` 也对用户这么承诺；但 DSH 侧 `DshAgentConfirmation.confirmSftpWrite()` 把 `approval.request()` 的四种结果**统一映射为 `'once'`**（`confirmation.ts:110`），因为 `ctx.approval` 的词汇只有 `allowed-once`/`rejected`/`cancelled`/`unavailable`。**结果是文档承诺的两档授权在 DSH 上根本不存在。**
- **做法**：`confirmSftpWrite` 改成两步——先 `userQuestions.ask()` 让用户选范围（`仅本次` / `此目录 15 分钟` / `本会话`），再把结果回填 `SftpWriteScope`；`ctx.approval` 只用于「是/否」（删除、敏感路径二次确认）。
- **收益**：既恢复产品差异化（按目录授权 + 越界高亮），又不再对用户说假话；同时顺手解决「多服务器时 `serverId` 缺失」的隐式目标问题——读/写工具在 `serverId` 省略且**已连接多于一台**时，用 `ask()` 让 Agent 拿到明确目标，而不是落到 `resolveServer()` 的「最近连接」兜底（`AgentToolService.ts:415-429`）。
- **约束/验收**：`userQuestions` 需要配置 responder（web 有 `ui-user-questions`），无 responder 时 `NO_PROVIDER`——必须 catch 并降级为 `once`。验收：选「此目录 15 分钟」后，同目录第二次写**不弹窗**，跨目录写**弹窗且无「本会话」选项**（与 `resolveAllowedScopes` 的敏感/越界分支一致）。

### R11 `settings.plugins.tab`：给插件一个真正的运维面板

- **接口**：向 `settings.plugins.tab` 注册 `{ id, order, label }` + keyed body；分区壳由 `ui-settings-plugins` 拥有（`dsh-web-app:432` 已挂），只有一个贡献时直接渲染为页面。
- **现状**：插件只有 8 个自动生成的设置字段（`dsh/settings.js`），运维态信息（信任库多少条、哪些主机指纹变更待处理、审计文件多大、上次连接失败原因）散落在终端面板与日志里。
- **做法**：一页三段——「连接健康」（SSH 失败分类统计、`idleDisconnectMinutes` 是否真的生效）、「信任库」（`HostKeyStore` 列表 + 一键 forget，复用 `terminal.forgetHost`）、「审计」（`agent-audit.jsonl` 尾部 + 导出）。
- **约束/验收**：本机 profile 的 `ui-settings.enabled: false`（`~/.dsh/profiles/desktop/cordis.patch.yml`）只关闭**开发者工具/HTML 预览权限**，不卸载设置外壳（`ui-settings` README 明确该字段「控制界面展示和 HTML 预览权限，不控制 Host 授权或 Session 记录」）；但分区是否可达仍应用 `cordis_inspect_query` 查 `settings.plugins.tab` 的 owner 与当前注册项。样式只允许 `--dsw-alias-*` token，禁止 import 任何 client 包（本仓库已有硬约束）。

### R12 客户端启动体积：1 MB 单文件 + `immediately: true`

- **接口**：`dsh.client.immediately`（graph 行上的「启动即加载」标记）；官方 `ui-sidebar-terminal` 用 `require.async('./client.terminal.js')` 把 xterm **分块按需加载**。
- **现状**：`dsh/client.js` = 1 022 576 B 单文件、`immediately: true`、xterm 5.5 + webgl/fit/search/web-links 全部内联（`esbuild.dsh.mjs:126-148`，`external: ['react']` 之外全内联）。任何 Harness 页面启动都为「可能永不打开」的终端面板付这笔钱。
- **做法（两条路，先做便宜的那条）**：
  1. `immediately: false` + 首次打开面板时再 `load`（验证 slot 注册是否仍能懒装；若不行则退回 2）；
  2. 拆 chunk：xterm 引擎 + 4 个 addon 单独产物，`require.async` 引入（照抄官方 `client.terminal.js` 的做法）。
- **收益**：启动载荷预计从 ~1 MB 降到 ~150–250 KB（xterm 主体 `lib/xterm.js` 289 KB + webgl addon 101 KB + search 12 KB 是主要可延迟部分；其余是本插件的视图/样式），首次打开终端多一次一次性的 chunk 请求。
- **约束/验收**：`esbuild` 的 `format: 'cjs'` 单文件产出**不支持** code-splitting，必须改成 ESM + 自建 `require.async` 垫片（官方就是 `require.async`）；`verify.mjs` 的「VM 执行 factory 断言无副作用」检查必须同时接受分块。验收：`web boot` 前后 Network 面板对比 + 终端首次打开可用。

## 5. D 组：一致性与安全修补

### R13 给自建 HTTP 载体加 Host/Origin 围栏

- **证据**：`dsh-host-webserver` README 明确「**不提供服务器级认证或来源策略**：其他 route owner 会实施自己的请求策略」；而 `dsh/client-connection` 实现了完整的 `isTrustedApiRequest()`（Host 白名单 + `sec-fetch-site: cross-site` 拒绝 + Origin 同源）。
- **本插件现状**：`dsh/channel.js` 里 `headers.origin` / `sec-fetch` / `401` **零命中**；`rpc` 处理器**不校验 `content-type`**，只要 body 能 `JSON.parse` 就分发（`dsh/channel.js:741-815`），请求体上限 **384 MiB**（`dsh/channel.js:119`）。路由覆盖 SFTP 读写、服务器 CRUD（口令值不回传但可覆写）、资产导入导出。
- **为什么这在默认回环下仍然值得修**：默认 `host: 127.0.0.1`（`dsh-web-app:179` 行的 `host: !!js ctx.webStartup.host ?? '127.0.0.1'`），但
  1. 任意网页可以用**简单请求**（`content-type: text/plain`，无预检）向 `http://127.0.0.1:<port>/dsh-at-terminal/rpc` POST 一个 JSON body——`no-cors` 只挡**读响应**，不挡副作用，`servers.remove` / `sftp.delete` / `sftp.writeFile` 照样生效（CSRF）；
  2. DNS rebinding 可进一步让读取响应也成为可能；
  3. `webStartup.host` 可以指向非回环地址（局域网/容器），此时同网段任何人可直达。
  所以这不是「假设用户配错」，而是「默认配置下缺一道浏览器侧本可提供的围栏」。
- **做法**：照抄 `isTrustedApiRequest` 的三条判定（Host 必须回环或等值、`sec-fetch-site !== 'cross-site'`、Origin 与 Host 同 authority），失败回 403；`rpc` 增加 `content-type: application/json` 校验；`ws` 升级同样校验 `Origin`。可选：boot 时生成一次性 token 注入 `window.__AT_TERMINAL_TOKEN__`，`rpc`/`ws` 皆校验（对 `dsh-app://` 页面同样可行，因为 `channel.info` 已经是 Host 下发的）。
- **收益**：把「本机回环假设」变成「显式围栏」；与 `verify.mjs` 的既有 9 项门禁同一风格，可加第 10 项（静态断言 `channel.js` 含 origin 校验）。

## 6. 不做清单（与既有产品边界一致，附证据）

| 不做 | 理由（取证） |
|---|---|
| 用 `ctx.fs` 做远程文件系统 / FileSystemProvider 全量挂载 | `ctx.fs` 是**单例服务**（`super(ctx,"fs")`），`fs-sandbox` 已占位；没有多 provider 的接缝。上游 `dsh-fs-ssh` **未随包发布**（`app.asar` 0 命中） |
| 替换 `ctx.subprocess` 把官方终端路由到 SSH | 一个组合只能有一个 subprocess provider（本仓库 `dsh/README.md` 已记录该结论）；正确做法是 R6 的 `ctx.terminals` backend |
| 把本地端口转发暴露成 Agent 工具 | 产品红线（`docs/handoffs/IMPLEMENTATION-CONTRACT.md`），且 `LocalPortForward.ts` 在 dsh 侧**零消费者** |
| 合并终端 / Agent / SFTP 到同一条 SSH 连接 | 同上红线；当前 `SftpAgentService` 的连接池 + `RemoteCommandExecutor` 的 lease 语义已经足够 |
| 自己实现 Typert Remote（`ctx.typertGateway`）替代 HTTP 载体 | `dsh-typert-registry` 的 `register(contribution)` 确实接受运行时描述符，但 Client 侧 `ctx.remote.$mount()` 要求**生成的严格 codec**，跨 release 稳定性无保证。建议保持 HTTP，先把 R13 的围栏补齐；把 Typert 列为 P3 探索，验收标准写成「跨一个 rc 升级不需要重编生成物」 |
| 递归目录删除做成 MCP/Agent 工具 | 上游红线；若要放开，按 R14-⑥ 用 `recursive` 显式参数 + 计数确认，不做事后补语义 |

## 8. 度量与验收口径

| 维度 | 基线（本次实测） | 目标 | 测量方式 |
|---|---|---|---|
| 工具定义体积 | 7 811 B | ≤5 400 B | 按完整键名数组序列化，脚本化对比 |
| 客户端启动载荷 | 1 022 576 B（`immediately: true`） | ≤300 KB 或延迟加载 xterm | `web boot` Network 面板 + `dsh/client.js` 体积 |
| 命令超时可识别性 | 超时只关流，远端进程存活 | `TOOL_TIMEOUT` + 后台可 `job_kill` | 用 `sleep 60` + pidfile 验证 |
| 审计可追溯 | 内存 50 条，刷新即丢 | JSONL 落盘 + 会话事件可回放 | 一次调用后文件行数 + `tools/result` 观察日志 |
| 授权语义 | 仅 `once`（文档承诺三档） | 三档可选 + 跨目录无「本会话」 | 手工走查 + 单测 `resolveAllowedScopes` 的 dsh 映射 |
| 护栏覆盖 | 0 个 guard | 15/15 工具在覆盖表 | `verify.mjs` 静态断言 |
| 设置项有效率 | 8 项中 2 项无消费者（`sessionLogDirectory`/`idleDisconnectMinutes`） | 8/8 有消费者或被移除 | 静态 grep + 单测 |

## 9. 一句话总结

这个插件已经把 **「DSH 怎么装一个插件」** 做对了（双半、effect 归属、错误分层、设置 schema、9 项门禁）；下一步的价值不在再写一个工具，而在**把 DSH 0.2 已经提供、而本插件空着的六个语义接缝补上**：提示词段（R1）、斜杠命令（R9）、工具护栏（R3）、结果观察者（R4）、后台任务（R5）、会话投影/持久终端（R6）。前四项合计约一周，能同时解决「token 常驻过高」「授权只在工具内部」「事后无证据」三个结构性短板。
