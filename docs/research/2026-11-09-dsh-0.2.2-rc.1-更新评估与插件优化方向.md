# DSH 0.2.2-rc.1 更新评估与 AT Terminal 优化方向

> 评估日期：2026-11-09  
> 评估对象：`at-terminal-dsh` 0.3.0（本机以 `link:` 方式挂在 `desktop` profile）  
> 已安装 Harness：**DeepSeek Harness Desktop 0.2.2-rc.1**（2026-11-04 构建）  
> 取证方式：`app.asar` 内 `@deepseek-ai/*` 包清单与 README、GitHub Releases、`npm run verify:dsh`、`npm run verify:kernel`、`npm run typecheck`、`npm test`  
> 落地计划：[`docs/plans/2026-11-09-dsh-0.2.2-rc.1-优化实施计划.md`](../plans/2026-11-09-dsh-0.2.2-rc.1-优化实施计划.md)

## 0. 结论摘要

DSH 当前最新一次更新是 **v0.2.2-rc.1（2026-11-04）**，前一版是 v0.2.2-alpha.3（2026-11-03）。这不是一次只改 UI 的版本：它同时改了**工具条件启用协议、插件包兼容性判断、文件修改保护默认值、插件更新/回滚机制和 Cordis 运行时**，对 AT Terminal 这类“工具 + 右侧栏面板 + 可选组合包”的插件影响很直接。

本仓库当前状态（实测）：

| 检查 | 结果 |
|---|---|
| `npm run verify:dsh` | **10/11 通过，1 项失败**：vendored `@deepseek-ai/schemastery` 3.18.5，但 0.2.2-rc.1 已带 3.19.0 |
| `npm test` | **101 个文件、1437 个用例中 2 个失败**：`test/docs/hostVersion.test.ts` 的 README / `dsh/README.md` 仍写 `0.2.1-rc.5`，实际安装是 `0.2.2-rc.1` |
| `npm run typecheck` | 通过 |
| `npm run verify:kernel` | 4/4 通过 |

按优先级，我认为最值得做的方向是：

1. **先做兼容收口**：升级 vendor 的 schemastery/cosmokit、修补 `dsh/package.json` 的发布文件清单、补 `engines.dsh`/`engines.node`/`dsh.manifestVersion`、同步 README 的宿主版本声明。工作量很小，但不做会直接卡住发布门禁和后续第三方包更新；其中发布文件清单缺失会让 npm 包根本无法 `import`。
2. **补远程编辑原语**：新增 `at_terminal_sftp_edit_file`（单文件字面量替换/`replace_all`），再考虑 `at_terminal_sftp_apply_patch`（多文件 Codex 风格补丁）。这是插件当前相对 DSH 本地工具面最大的能力缺口——本地已有 `read` / `write` / `edit` / `apply_patch`，远程只有整文件覆盖。
3. **给 Agent 侧 SFTP 写增加版本防护**：`read_file` 已经返回 `size` 和 `modifiedAt`，但 `write_file` 只认 `overwrite: true`。应支持 `expectedSize`/`expectedModifiedAt`，并对不上时返回类似 `FS_STALE_VERSION` 的稳定错误，避免静默覆盖别人刚改过的远端文件。
4. **收口 `at_terminal_job_output` / `at_terminal_job_kill`**：插件后台任务本来就走 `ctx.jobs`，而 0.2.2 的 standard/cordis/ptc preset 都挂载了官方 `job_output` / `job_list` / `job_kill`。这两个工具既重复（约 630 B schema，≈158 token），又可能和宿主的任务完成通知产生“谁先消费输出”的竞争；建议用 `when` 条件注册，仅在宿主 job 工具对当前 agent 不可见时暴露（保留 minimal/custom 组合的 fallback，不要直接删除）。顺手修正两个真实缺陷：`at_terminal_job_output` 的 90 s tool timeout 小于它允许的 600 s `wait` 上限；`dsh/jobs.js` 在远端 kill 报告返回前就 `abort` 并把 job 结算成 `killed`，文案“process group is gone”并不成立。
5. **用 `ctx.tools.register(definition, { when })` 做工具条件化**：17 个工具目前每个请求都常驻。无服务器/未配置服务器的会话可以只保留 `ping` 与 `list_ssh_servers`，把其余工具和 `at_terminal` 提示词段一起隐藏，预计每次请求省约 1.2k token。
6. **补热更新生命周期**：`dsh/index.js` 的平台清理 disposer 没有返回并等待 `handle.close()`，且 `createDshPlatform` 是 fire-and-forget；DSH 0.2.2 的插件更新/回滚先停旧版再装新版时，可能留下 `at_terminal_state` 的 `already-open`。同时 `dialogLanguage` 在 Loader 1.1 的 volatile-only 更新下不会重新读取，设置改了要等重启。

再往下的 UI 新接缝（统一右键菜单、file actions/file drag、文件预览常驻目录树）属于下一版本，不要和 P0 兼容收口混在一起。

## 2. 插件现状核对（实测证据）

### 2.1 版本与门禁

- `package.json` / `dsh/package.json`：`@at-series/dsh-at-terminal@0.3.0`。
- `README.md:6`：DSH badge 写 `0.2.1-rc.5_Verified`。
- `dsh/README.md:9` 与 `:635`：仍写 `0.2.1-rc.5`。
- 本机 `Info.plist` 的 `CFBundleShortVersionString`：`0.2.2-rc.1`。
- `dsh/scripts/verify.mjs` 已能读出宿主版本并把 `dsh-tools` 契约跑到 0.2.2-rc.1（17 个工具全部通过 schema 校验），但**没有校验 `engines.dsh` 是否覆盖宿主**。
- `dsh/package.json` 的 `files` 清单漏了 7 个实际被相对 import 的运行时模块（`jobs.js`、`locale.js`、`optionalBundle.js`、`policy.js`、`prompt.js`、`skills.js`、`spill.js`），而 `scripts/release.mjs` 会把 `dsh/` 作为 npm 包发布——这是比 `schemastery` 更严重的“装不上/加载不了”问题。

`npm test` 的实际结果：`Test Files 1 failed | 100 passed (101)`，`Tests 2 failed | 1435 passed (1437)`，失败用例就是 `test/docs/hostVersion.test.ts` 的两条 README 版本断言。

`npm run verify:kernel`：4/4 通过。`npm run typecheck`：0 错误。

### 2.2 工具体积实测

用 `createTools()` 组装 17 个工具，按 `{name, description, parameters}` 序列化：

| 指标 | 值 |
|---|---:|
| 17 个工具总字节 | **5,352 B** |
| 约 token（按 4 B/token 粗算） | **≈1,338 token** |
| 最大单项 `at_terminal_open_monitor` | 487 B |
| `at_terminal_sftp_write_file` | 482 B |
| `at_terminal_run_remote_command` | 447 B |
| `at_terminal_job_output` + `at_terminal_job_kill` | 630 B（≈158 token） |
| `PROMPT_SECTION_TEXT` | 1,751 B（≈438 token） |

分组看：8 个 SFTP 工具合计 **2,767 B（≈692 token）**，job 对 **630 B（≈158 token）**，其余 7 个 **1,955 B（≈489 token）**。也就是说，一个完全没有 SSH 需求的会话，也会为 AT Terminal 固定支付约 **1,750 token**（工具 schema + 提示词段）。条件工具是 0.2.2 给插件的最直接省钱接口。

### 2.3 插件已经做对、不要重复造的部分

这次审计一个很重要的结论是：0.3.0 已经把前一轮建议的“语义接缝”基本补齐，不要把这些当成新问题：

- `ctx.tools.guard()` + `tools/pre-execute`：`dsh/index.js:206`。
- `tools/result` 审计 + `agent-audit.jsonl`：`dsh/index.js` 的 audit effect。
- `ctx.jobs`：`dsh/jobs.js` 是 job producer，`run_remote_command` 的 `run_in_background` 已接入。
- `ctx.spillStore`：`dsh/spill.js` 已把超限结果交给宿主 spill store。
- `ctx.systemPrompt.section()` / `variable()`：`dsh/prompt.js` 已注册 `tool:at-terminal` 段与 trust 变量。
- `ctx.skills.register()`：三个运行时技能已注册（本会话 ping 报 `registered 3/3`）。
- `ctx.commands.register()`：`/ssh-metrics`、`/ssh-audit`。
- 可选 `type: "ssh"` 的 `ctx.terminals` backend：`dsh/terminal.bundle.js` + `cordis:group` + `isolate: { terminals: true }`。
- `settings.plugins.tab` 设置页、信任库、决策统计。
- HTTP/SSE/WebSocket 通道已有 Host/Origin/Sec-Fetch-Site/content-type 围栏（0.3.0 新增）。
- 多服务器写/执行 `serverId` 缺失拒绝与 `resolvedBy` 回显。
- `at_terminal_sftp_write_file` 的 `localPath` 大文件流式上传。

因此本轮优化应集中在 **DSH 0.2.2 新增的接口** 与 **远程编辑/安全缺口**，而不是重新做一遍 0.3.0 已完成的接缝。

## 3. 优化方向

### P0-1 升级 vendored schemastery / cosmokit，恢复 `verify:dsh` 全绿

**现状**：宿主 0.2.2-rc.1 实际带 `@deepseek-ai/schemastery@3.19.0` 与 `@deepseek-ai/cosmokit@1.9.0`；`dsh/scripts/vendor.mjs:56-67` 仍钉 `3.18.5` / `1.8.6`。`verify.mjs` 对两个包都做版本比对，所以不能只改一个。

**做法**：

1. 更新 `dsh/scripts/vendor.mjs` 的 `VENDORED` 两项：

```js
{
  name: '@deepseek-ai/schemastery',
  version: '3.19.0',
  integrity: 'sha512-bDXoYQa7ghAhmdYD5VPlzKxEzJV/aKkz5l4V5h1u06z8GAPN1ROewSjvR9WiXhpa52E9fng8lpH5QdCRIQgnyQ=='
},
{
  name: '@deepseek-ai/cosmokit',
  version: '1.9.0',
  integrity: 'sha512-5O1S53mZiJyZYcvxxD0Qv1EY7qFPSxbGyD8CbVK6gw7W9FvcXZj2YIX1ZkOqyQQ3Xt2rFkZDHJv0+V3Zmmp8CA=='
}
```

2. 执行 `npm run vendor:dsh` 重新落盘 `dsh/node_modules/@deepseek-ai/*`。
3. 执行 `npm run verify:dsh`，应为 11/11。

**收益**：恢复发布门禁；避免 schemastery 3.19 与 3.18 在 `.volatile()` / 配置校验上的行为差异在真实设置写入时才暴露。  
**风险**：极低；vendor 脚本本身会校验 SRI。  
**工作量**：XS。

### P0-2 修复 `dsh/package.json` 的发布文件清单与 vendored 依赖打包

**现状（严重）**：`dsh/package.json:14-29` 的 `files` 只列出 `index.js`、`tools.js`、`settings.js`、`channel.js`、`commands.js`、`client*.js`、`host.bundle.js`、`terminal.bundle.js`、`cordis.patch.yml`、`icon.svg`、`locale/*.json`、`policy-assets`；但实际运行时入口还相对导入了：

- `dsh/tools.js:27-32`：`settings.js`、`policy.js`、`spill.js`、`prompt.js`、`skills.js`、`jobs.js`

### P0-3 补 `engines.dsh` / `engines.node` / `dsh.manifestVersion`，并同步宿主版本文档

```json
}
```

- 在 `dsh/package.json` 的 `dsh` 对象加 `"manifestVersion": 1`；`dsh-terminal-ssh/package.json` 也同步加相同的 `engines`（它也是 DSH 要加载的 bundle）。

- 在 `dsh/package.json` 的 `dsh` 对象加 `"manifestVersion": 1`。
- 更新 `README.md:6` 的 badge、`dsh/README.md:9` 与 `:635` 的 “Verified against” 为 `0.2.2-rc.1`。
- 顺手更新 `dsh/settings.js` 顶部注释与 `dsh/scripts/vendor.mjs` 注释里对 `0.1.7-rc.2` 的旧描述（不影响功能，但会误导后来读者）。

### P1-0 修复平台装配的异步清理，避免热更新/禁用后 `storageDomain already-open`

**现状（热更新风险）**：`dsh/index.js:545-550` 的平台生命周期清理是：

```js
scoped.effect(() => () => {
  sftp.dispose()
  void handle.close()
}, 'at-terminal: platform lifetime')
```

`handle.close()` 是 async（`src/platform/dsh/index.ts:98-104`），但 disposer 没有返回它；Cordis 4.1 只有 disposer 返回 Promise 时才会等待清理完成。`src/platform/dsh/state.ts:137-140` 打开的 `at_terminal_state` 在关闭完成前仍处于 `already-open` 状态；DSH 0.2.2 的第三方插件更新/失败回滚会先移除旧版本再安装新版本（`dsh-plugin-manager` 0.2.2 行为），于是新版本可能打不开状态域。另一个竞态：`dsh/index.js:448-475` 的 `createDshPlatform(...).then(...)` 与 `:624` 的 `void assembled` 是 fire-and-forget，如果插件在装配完成前被禁用，`.then` 里的 effect 注册不会执行，`handle.close()` 也永远不会调用。

**建议**：

1. disposer 返回关闭 Promise：

```js
scoped.effect(() => () => {
  sftp.dispose()
  return handle.close()
}, 'at-terminal: platform lifetime')
```

2. 在 `createDshPlatform` 之前设置 `disposed` 标志；`.then((handle) => { if (disposed) return handle.close(); ... })`，并在插件卸载时等待装配 Promise settle（或 abort 装配）后再完成清理。
3. 加一个真实测试：启用插件 → 等待 `at_terminal_state` 打开 → 禁用/重载 → 再次启用，确认不再出现 `storageDomain already-open`。

**收益**：让 DSH 0.2.2 的插件更新/失败回滚真正可用；避免用户必须重启 DSH 才能再次启用插件。  
**风险**：清理顺序要保证 `sftp.dispose()` 先于 platform close（现有顺序正确），并处理装配未完成的 handle。  
**工作量**：S–M。

### P1-1 新增 `at_terminal_sftp_edit_file`（远程单文件编辑）

**为什么重要**：这是相对 DSH 本地工具面最明显的缺口。DSH 的 `dsh-tool-fs` 早已有 `write` / `edit`，0.2.2 又加了 `apply_patch`；而 AT Terminal 的 Agent 侧只有 `sftp_read_file`（最多 256 KiB 窗口）和 `sftp_write_file`（整文件 content）。对一个大配置文件，模型必须先读完整文件、再整文件重写——既费 token，又很容易因为没读全而截断文件。

**建议接口**（与 DSH `edit` 语义对齐）：

```text
at_terminal_sftp_edit_file
  serverId?: string
  path: string
  oldString: string        // 必填，唯一字面量匹配（除非 replaceAll）
  newString: string        // 替换文本，可为空（删除）
  replaceAll?: boolean
  expectedSize?: integer
  expectedModifiedAt?: integer
```

**实现要点**：

1. 复用 `SftpAgentService` 的 `resolveTarget` / `leaseFor` / `resolveWritablePath`，走现有的 `requireWrite` 授权与审计。
2. 读取目标文件（建议上限 2 MiB，与 `SFTP_TEXT_MAX_BYTES` 一致；超过则返回明确错误，建议模型用 read 窗口查看后再决定）。
3. 检测 NUL 字节拒绝二进制；检测 CRLF 并归一化为 LF 后匹配，写回时恢复 EOL（复用 `src/platform/dsh/sftp.ts` 的 `eol` 规则）。
4. `oldString` 出现 0 次或（未给 `replaceAll` 时）多于 1 次 → 返回可操作的错误（`Found 0 occurrences` / `Found N occurrences; pass replaceAll or provide a longer match`）。
5. 写入前执行版本检查（见 P1-2）；建议 temp 文件 + rename 的原子写（若服务端支持 `posix-rename`；否则至少保留原文件备份策略并在失败时说明）。
6. 返回值建议包含：`path`、`replacements`、`bytesWritten`、`size`、`modifiedAt`，并在 `output.render` 里给出 diff 摘要（可选）。

**收益**：大文件编辑从“读全文件 + 整文件写”变为“读一次 + 一段 old/new”；模型上下文与人工审批都更小；和 DSH 本地 `edit` 的行为一致，模型不需要学一套新语义。  
**风险**：需要处理 EOL、二进制、并发和原子性；应新增单测覆盖 CRLF、0/多匹配、二进制、版本冲突。  
**工作量**：M。

### P1-2 给 Agent SFTP 写/编辑/删除加远端版本防护

**现状**：`at_terminal_sftp_read_file` 的返回值已经带 `size` 与 `modifiedAt`（`dsh/tools.js:864-875`）；UI 的 `sftp.writeFile` 也已经支持 `expectedSize` / `expectedModifiedAt`（`src/platform/dsh/sftp.ts:157-164`，冲突检查在 `:70-73`）。但 Agent 的 `SftpAgentService.writeFile`（`src/agent/SftpAgentService.ts:303-340`）只检查 `exists && !overwrite`，完全不比对版本。

**建议**：

**风险**：额外一次 `stat`；配置默认值需要兼顾旧行为。  
**工作量**：S–M。

### P1-3 收口 `at_terminal_job_output` / `at_terminal_job_kill`

**现状**：

- 插件后台任务通过 `ctx.jobs.start()` 注册（`dsh/jobs.js`），`kind: 'ssh-command'`；任何宿主 job 工具都能按 id 读取/终止它们。
- `dsh/tools.js:1557-1701` 又注册了 `at_terminal_job_output` / `at_terminal_job_kill`，与宿主 `job_output` / `job_kill` 功能重复；宿主的 `job_output` 还支持“用户插话立即解除等待并返回当前输出”，插件版本没有这一行为。
- DSH 0.2.2 的 standard、cordis、ptc preset 都挂 `@deepseek-ai/dsh-tool-jobs`（`dsh-web-app/presets/*.patch.yml`）；只有 minimal preset 不挂——但 minimal 里没有 job controller，`jobs.start()` 本来就会拒绝，后台执行自动降级为前台，所以插件自己的 job 工具在那种组合里也没有可服务的 job。
- `dsh/README.md:34` 仍写着“desktop composition ships tool-jobs disabled”，这一说法在 0.2.2 的 preset 层面已经过时（`dsh-web-app/cordis.patch.yml` 只是 base 层 disabled，standard/cordis/ptc preset 会重新开启）。
- **命名不一致**：`dsh/tools.js:544` 的 background render 让模型使用宿主名 `job_output` / `job_kill`，而 `dsh/prompt.js:50` 与 `dsh/skills.js:45` 又让模型使用 `at_terminal_job_output` / `at_terminal_job_kill`；两套工具同时存在时，模型会收到互相矛盾的指令。
- **超时上限不一致**：`at_terminal_job_output` 的工具级 `timeoutMs: 90000`（`dsh/tools.js:1562`）小于它允许的 `wait` 上限 600000（`dsh/tools.js:1615`）；模型请求较长等待时，会先被宿主 timeout policy 以 `TOOL_TIMEOUT` 打断，而不是按工具自己的等待语义返回 `[status: running]`。
- **杀停语义过强**：`dsh/tools.js:1648-1649` 写“killed means the remote process group is gone”，但 `dsh/jobs.js:155-173` 的 `cancel` 只是触发 `terminateRemoteCommand(...)` 后立即 `controller.abort()`；`jobs.kill` 本身返回的是 `requested`，远端 kill 报告尚未到达时 job 已按 `killed` 结算，“gone”并没有被证明。页面上的 stop 控件同样会因此过早显示终止。

**建议**：

- **优先条件注册**：保留 `at_terminal_job_output` / `at_terminal_job_kill` 的定义，但用 `when` 只在“`ctx.jobs` 存在且当前 agent 视图里看不到宿主 `job_output` / `job_kill`”时暴露；这样 minimal/custom 组合仍有 fallback，标准 preset 下不再重复。若实现条件判断的成本高于收益，再考虑默认移除并在 README 说明背景执行依赖宿主 `tool-jobs`。
- 把 `dsh/prompt.js` 中的 “collect it with at_terminal_job_output, end it with at_terminal_job_kill” 改为宿主的 `job_output` / `job_kill`，并补一句“完成通知会直接携带小输出，不要无脑轮询”；`dsh/skills.js` 的巡检技能也改成“使用当前工具表中可用的 job 工具”，不要硬编码。
- 若保留插件 job 工具，修正两个正确性问题：`at_terminal_job_output` 的 `timeoutMs` 至少覆盖 `wait` 上限（≥600000，或把 `wait` 上限压到 85 s）；`dsh/jobs.js` 的 `cancel` 延迟 `controller.abort()` 到 `terminateRemoteCommand` 的 `finally`，或在工具文案里改成“kill 已请求，状态以 job 快照为准”，不要声称进程组已消失。
- 更新 `README.md` / `dsh/README.md` 的工具表和 `CAPABILITIES`（`background-jobs` / `job-control` 能力仍存在，只是不再由插件提供控制工具）。

**收益**：每请求省 630 B（≈158 token）；消除“插件 job 工具 vs 宿主 job 工具”的消费竞争和重复通知风险；工具名和实际行为一致。  
**风险**：极少数自定义组合若只有 `dsh-jobs` 而没有 `dsh-tool-jobs`，本来也无法启动 job，无实际损失。  
**工作量**：S（条件隐藏）/ S–M（超时与杀停语义修正）。

### P2-1 远程 `at_terminal_sftp_apply_patch`（多文件补丁，可选）

**依据**：DSH 0.2.2 已把 `apply_patch` 做成正式工具（默认关闭），`@deepseek-ai/dsh-fs-patch` 提供 `parsePatch` / `applyHunks` 两个纯函数，`dsh-tool-fs` 的 `apply-patch` 实现是“语法/匹配/缺失文件全量预检 → 顺序提交 → 首个失败停止，保留已生效部分”。这套设计可以直接复用到远程。

**建议**：

- 新增 `at_terminal_sftp_apply_patch`，参数 `serverId?`、`path`（远端基准目录）、`input`（Codex 风格 `*** Begin Patch` 文本）；默认关闭，设置 `enableApplyPatch: false`，因为工具 schema 和多文件审批都有成本。
- 预检阶段：对每个 Add/Update/Delete/Move 目标 stat/read；用 `parsePatch` + `applyHunks` 在内存模拟；任何一个语法/hunk/文件错误都阻止全部写入。
- 提交阶段：按顺序通过 `SftpAgentService.editFile` / `writeFile` / `deleteFile` / `rename` 执行；每个文件走现有授权；返回 `phase`、`cancelled`、`operations[]`（`status: completed | failed | unknown | skipped`）与 `affectedPaths`。
- 依赖处理：`@deepseek-ai/dsh-fs-patch` 是 npm 发布的 0.2.2-rc.1 纯 JS 包，可精确钉版本并作为构建期依赖内联进 `host.bundle.js`，避免 `link:` 安装时 Node 解析不到 `app.asar` 内部包；如果打包成本高，再把 `parsePatch`/`applyHunks` 的 MIT 实现 vendoring 到 `src/sftp/patch/`。
- 不要把远程 patch 说成“Review 可看”：DSH 的 Review 面向本地 `ctx.fs`，远程只能由插件自己的结果/审计呈现，文档要诚实。

**收益**：模型可以用它已经熟悉的 Codex patch 语法一次改多个远端文件，减少往返和整文件 token；对“重构一组配置/脚本”场景价值最大。  
**风险**：SFTP 无事务，部分提交不可避免，必须如实返回每项状态；预检要模拟前序操作，否则看似通过、提交时失败；审批次数可能多。  
**工作量**：M–L（建议排在 P1-1/P1-2 之后）。

### P2-2 迁移到 `ctx.contextMenus` 统一右键/键盘菜单

**现状**：插件的资产列表和 SFTP 树各自维护一份右键菜单与 `useMenuFocus`（`src/platform/dsh/client/menuFocus.ts`），代码注释已经说明这是为了处理焦点、Escape、滚动锚点而重复实现的。DSH 0.2.2 的 `dsh-client-ui-context-menu` 已挂载在 web 应用里，正好覆盖这些问题。

**建议**：

1. 在 client `inject` 增加 `contextMenus`（并在 `dsh/package.json` 的 `dsh.client.inject` 增加 `@deepseek-ai/dsh-client-ui-context-menu`）。
2. 通过声明合并 `ContextMenuTargetMap` 增加两个目标种类，如 `{ kind: 'at-terminal.server', value: { serverId } }` 和 `{ kind: 'at-terminal.remote-file', value: { serverId, path, isDirectory } }`。
3. 用 `ctx.contextMenus.register` 注册动作：服务器行的连接/断开/监控/编辑；文件行的打开/编辑/下载/重命名/删除/复制路径；目录行的上传/新建文件。
4. 行组件改用 `getTriggerProps(target, handlers)` 处理右键、Shift+F10、ContextMenu 键和触屏；删除本地 `useMenuFocus` 的重复逻辑。

**收益**：菜单定位、视口/软键盘跟随、暗色主题、图标、快捷键联动、触摸都可复用宿主实现；插件代码减少，交互和 DSH 其他区域一致。  
**约束**：该包是 0.2.2 新增，迁移意味着最低支持版本要改到 0.2.2；若要兼容 0.2.1，必须用 optional inject 或 feature-detect，建议下一个 minor 直接放弃 0.2.1。  
**工作量**：M。

### P2-3 接入 `fileActions` / `fileDrag`：远程文件下载、拖入对话与拖拽上传

**现状**：插件 SFTP 页有自绘的上传/下载（`views/sftp.ts`、`body-session.ts:523-589` 的 `downloadSftpFile` 走自定义 RPC + base64 + `saveBytes`），但下载仍是自定义 RPC + Blob；DSH 已挂载 `dsh-client-ui-file-actions`（原生 `saveAs`、成功路径、Finder 定位）和 `dsh-client-ui-file-drag`（文件拖拽传递）。

**建议**：

- **下载（S/P1，可先单独做）**：用 `ctx.fileActions.save({ read: signal => fetchRemoteBytes(...), name, mediaType: 'application/octet-stream' }, 'download')` 替代自绘下载；Desktop 返回保存路径，Web 走浏览器下载；`saveAs` 仅在 Desktop 提供。保留 `saveBytes` 作为服务缺席时的 fallback，只在 `status === 'saved'` 时展示本地路径。注意 `file-actions` 不会把大文件变成流式——当前 `sftp.download` 仍是 base64 全量进浏览器内存，大文件仍受现有 `SFTP_TRANSFER_MAX_BYTES` 限制。
- **拖入对话（P3/M）**：在 SFTP 行上 `ctx.fileDrag.actions.prepare` 必须赶在 `dragstart` 同步事件之前完成异步预取；大文件会整份进浏览器内存，建议只对 ≤8–16 MB 的小文件、显式拖拽把手启用，超过上限回落为下载。移动端不支持时不要暴露。
- **拖拽上传**：给 SFTP 树加 HTML5 drop 目标，复用现有 `uploadSftpFiles`，不需要 DSH 接口；外部文件拖入直接读 `DataTransfer.files` 即可。

**收益**：更接近用户对桌面文件管理器的预期；减少自定义 Blob/下载代码；把“远程文件”接入 DSH 的附件流。  
**风险**：`fileActions.save` 的 `read` 回调会在浏览器侧缓冲字节，需限大小；拖拽跨平台差异。  
**工作量**：M–L。

### P2-4 SFTP 文件预览改成“常驻目录树 + 响应式分栏”

**现状**：`src/platform/dsh/client/views/sftpFile.ts` 明确选择“整页覆盖”，理由窄侧栏不适合对话框；DSH 0.2.2 的文档预览已证明可以在宽屏保留目录树、窄屏转为覆盖。  
**建议**：在 ≥560/768px 时在文件预览左侧保留 SFTP 树（复用现有 `SftpTree` 渲染），窄屏继续整页；保留当前树的展开状态、选中行和滚动位置；加 `Escape` 返回树、`Tab` 循环。收益：查看多个文件时不用每次回到树再展开；与 DSH 文件预览的操作习惯一致。工作量：M。优先级低于编辑/安全。

### P2-5 打包与插件管理细节

- `dsh/package.json` 的 `description` 很短，0.2.2 插件详情页支持富文本；可补一个面向用户的 `README.md`（npm 默认会带）、`repository`、`license`、`keywords`，让插件管理器的详情页不空白。
- 可选 bundle 安装 RPC 已返回 `outcome`（`dsh/channel.js:790-806`）；0.2.2 的 `installBundle` 还会返回 `pendingBuilds` / 诊断。设置页应把 `pendingBuilds` 的“需要批准构建脚本”提示出来，而不是只显示一个通用失败。
- `dsh/channel.js:799` 传入的 `{ activateNewBundles: true }` 不是 0.2.2 `installBundle` 的实际选项（它读取 `requestId`、`approvedBuilds`、`saveExact`、`enabled`、`registry` 等）；默认行为仍会安装并启用，但应删除死参数或改成显式 `{ enabled: true }`，避免未来默认值变化时失效。
- `describeOptionalBundle` 只读 `listBundles().enabled`（保存的选择），不代表激活成功；0.2.2 的安装结果应把 `pendingBuilds` / 激活错误 / `restoring` 等诊断一并回传设置页。
- `dsh-terminal-ssh/package.json` 也应补 `engines`，避免可选 bundle 在 future DSH 上绕过兼容检查。

### P3 观察项（不是本轮要做的）

1. **把 AT Terminal 变成 DSH 的远程执行环境（`ctx.fs` / `ctx.subprocess` provider）**：DSH 文档确实把“远端组合替换 fs/subprocess/sandbox 三个 provider”作为架构方向，但当前 0.2.2-rc.1 **没有随包发布 `dsh-fs-ssh` / `dsh-subprocess-ssh` 之类的 provider**；而且 `ctx.fs`/`ctx.subprocess` 是单例，一个组合只能有一个 provider，和 AT Terminal 的“多服务器资产”模型不完全匹配。上一轮 `docs/research/2026-10-21-dsh-扩展能力建议.md` 的“不做清单”仍然成立。建议保持观察：若 DSH 后续发布官方 SSH provider 接口或 `dsh-ssh` 包，再评估“把 AT Terminal 的服务器资产接到官方 FS/子进程层”，而不是现在重写。
2. **Session Projection**：0.2.2 把注册 API 改为异步。插件目前用 `agent-audit.jsonl` + 内存快照提供监控状态；projection 是从已提交 Session 事件日志折叠出的读模型，和插件的实时连接/传输状态不是一类数据。**不建议**为实时状态强接 projection；只有未来做“可回放的执行记录”时再评估。工作量 M，优先级低。
3. **`dsh-spill-policy` 双重 spill 观察**：base 组合已挂 `dsh-spill-policy`（`maxInlineTokens: 12500`），插件 `dsh/spill.js` 还有 32 KB 字符的自定义 spill；可能发生“插件先 spill、宿主再 spill”的双重处理。没有稳定服务可探测该策略是否挂载，建议保留 `dsh/spill.js` 作为无宿主策略时的 fallback，先观察是否出现重复 spill/额外文件，不要贸然删除。
4. **i18n/移动端/WebSocket 压缩/`JobKindMap` 本地化**：DSH 新增 6 种语言与移动端布局；插件只有 zh/en 字典，终端 WebSocket 是自绘的。属于体验打磨，等核心编辑能力稳定后再做。
5. **`dsh-client-ui-sidebar-documentpreview` 不建议用于远程文件**：它的文件读取依赖 Session workspace 的 `workspaceFiles.read/readBytes` 与资源地址，远程 SFTP 没有对应 resourceAddress；强行接只能落本地临时文件或自写自定义 renderer，带来数据副本与陈旧问题。插件自己的 `sftpFile.ts` 预览/编辑已够用，P2-4 只借鉴其“常驻目录树”的布局，不接它的读取层。

## 4. 不建议做 / 不要踩的坑

| 不做 | 原因 |
|---|---|
| 重写自建 HTTP 通道为 Typert Remote | `ctx.remote` 依赖构建期生成的严格 codec，跨 DSH rc 不稳定；0.3.0 已把 Host/Origin/content-type 围栏补齐，收益低风险高 |
| 现在替换 `ctx.fs`/`ctx.subprocess` 做远程 provider | 单例服务 + 无官方 SSH provider 包；会与 DSH 自带 `fs-sandbox`/`bash-local` 组合冲突，且远程语义（版本、symlink、原子写）工作量大 |
| 无条件增加工具 | 每个工具 schema 都按请求计费；新增 `edit`/`apply_patch` 应与条件化、配置开关一起设计 |
| 在 Host bundle 直接 import `@deepseek-ai/dsh-tools` 或其他 app.asar 内部包 | `link:` 安装时 Node 无法解析 app.asar 内部 `node_modules`；只能像 schemastery 一样精确 vendor，或构建期内联 |
| 让插件 job 工具与宿主 job 工具同时暴露 | 输出消费与完成通知可能双路径；优先宿主 job 工具 |
| 把远程 patch 说成能进 DSH Review | Review 只覆盖本地 `ctx.fs`；远程结果只能由插件自己的 UI/审计呈现 |
| 把 `dsh-tool-fs` 的 `apply_patch` 或 `dsh-tool-str-replace-editor` 原样当远程工具用 | 它们只操作 `ctx.fs` 本地文件系统，无法到达 SSH 服务器；远程编辑必须由 AT Terminal 的 SFTP 服务实现 |
| 采用已弃用的 `@deepseek-ai/dsh-agent-tool-presentation` | 0.2.2 的 README 已标注弃用，应直接使用 `dsh-tool-executor-native` / `dsh-tool-executor-ptc`；插件只用 `ctx.tools.register`，两者都兼容，不需要该包 |
