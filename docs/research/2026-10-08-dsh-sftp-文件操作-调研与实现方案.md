# DSH SFTP 文件操作：官方接口取证、同类实现调研与落地方案

> 轮次日期：2026-10-08
> 分支：`base-dsh`（起点 `81e917c`，工作区含前序未提交改动）
> 范围：把 `at-terminal-series` dsh 变体的 SFTP 面从「只读目录树」扩到 **上传 / 下载 / 查看 / 编辑**
> 涉及计划节点：DSH-16（Host 面第三服务）、DSH-23（文件树）、DSH-18（M2 集成测试）

---

## 0. 结论先行

| 问题 | 结论 |
|---|---|
| dsh 官方有没有现成的文件读写接口可以直接用？ | **没有**。官方的文件能力面向「会话工作区 + 本地磁盘」，全部是**只读**的（`dsh-client-ui-sidebar-files` / `dsh-client-ui-sidebar-documentpreview` 只读展示；`dsh-fs` 的写是给 Agent 工具用的，不是给面板用的）。远程 SFTP 文件既不在工作区内，也不是本地文件，官方接口**一条都套不上**。 |
| 那能力从哪里来？ | 走**已有的自建 RPC 通道**（`POST /dsh-at-terminal/rpc`）。`SftpManager` 早就拥有全部读写原语（`readFile`/`writeFile`/`stat`，见 `src/sftp/SftpManager.ts`），本轮只是把它们**暴露出来**，没有重写任何领域逻辑。 |
| 官方接口里有哪些**必须吸收**的约束？ | 三条硬事实（§1.4）：二进制判定的窗口是**前 8192 字节含 NUL**；文本预览上限是 **2 MiB**（分页 5000 行、整档 32 MiB）；本地文件能力是**只读**的。 |
| 最容易踩的坑是什么？ | **`<textarea>` 会把 CRLF 静默归一化成 LF**（W3C 规范行为）。不做处理的话，「打开一个 Windows 换行文件 → 保存」会改写每一行，产生一个用户没要求的全文件 diff。已在协议层用 `eol` 字段解决（§3.2）。 |
| 没做什么？ | 重命名 / 删除 / 新建文件 / 新建目录 / 目录递归下载。`SftpManager` 四个原语都在，这是**范围决策**不是能力缺口（§5）。 |

## 1. dsh 官方接口取证（真源：`app.asar` 产物）

一切以本机安装的产物为准，包路径都在
`/Applications/DeepSeek Harness.app/Contents/Resources/app.asar` →
`/dsh/node_modules/@deepseek-ai/**`，用仓库自带的 `dsh/scripts/lib/asar.mjs` 读取。

### 1.1 相关的 6 个包

| 包 | 角色 | 对本功能是否有用 |
|---|---|---|
| `dsh-client-ui-sidebar-files` | 右侧栏「工作区文件树」tab（`kind: files`） | ❌ 只列**会话工作区**目录；官方自己文档写明「**只有列目录**：没有搜索、产物过滤、拖拽、重命名、右键菜单」 |
| `dsh-client-ui-sidebar-documentpreview` | 文件预览（`dsh-resource://file/...` 地址的解析方） | ⚠️ 描述了官方**文本/二进制判定与上限**，是重要的对齐依据；但它的 provider 是**只读**的 |
| `dsh-api-workspace-files` | 上面两者背后的 Remote 命名空间 `remote.workspaceFiles.list(sessionId, absPath)` | ❌ 只能 `list`，且**拒绝工作区之外的路径** |
| `dsh-fs` / `dsh-fs-local` / `dsh-tool-fs` | Host 侧文件系统 seam 与 Agent 工具 | ❌ 是给模型用的工具面，不是 UI 面；且只覆盖本地 FS |
| `dsh-client-file-upload` | 浏览器文件 → Session 的**流式上传**（`ctx.fileUpload.upload(sessionId, body, name, signal, onProgress)`） | ❌ 语义不对：它把文件作为**提示词附件**暂存给 Agent，凭证以「接收方 Agent 的 Session 对象」为键，**不能指定远端路径**，也不能写进 SFTP |
| `dsh-host-directory-picker` + `dsh-client-ui-directory-picker-{native,browse}` | 工作区目录选择 seam（`ctx.directoryPicker`） | ❌ 选的是**目录**（用于指定 workspace），不是文件；且 native 后端要求操作者坐在宿主屏幕前 |

**关键结论**：dsh 官方**不提供**任何「把浏览器里的文件写到某个任意远端路径」或「把任意远端字节交给浏览器保存」的接口。这类能力**只能由插件自己的 RPC 通道承担**——这也正是本轮的实现路径。

### 1.2 官方的「打开一个文件」机制（读到了，但用不上）

官方文件树点击一个文件走的是**资源地址**：

```js
// dsh-client-ui-sidebar-files: file 行
tab.actions.openResource(
  `dsh-resource://file/session/<sessionId>/<相对工作区根编码后的路径>`
)
```

地址由 `@deepseek-ai/dsh-util-workspace-path` 的 `fileAddressFor(绝对路径, 树根)` 生成，由注册了 `patterns` 的 tab 类型接管。

**为什么套不上**：这个地址的语义是「**会话工作区内的**本地文件」。我们的目标是远端 SFTP 文件——它既不在工作区里，也不在本机磁盘上。硬造一个 `dsh-resource://` 计划地址只会得到一个「路径在工作区之外」的拒绝。

⇒ 因此本轮的查看/编辑器是**插件自己 tab 内的一个页面**（`views/sftpFile.ts`），不依赖官方的预览/编辑器。

### 1.3 `dsh-client-file-upload` 的能力与限制（原文摘录）

> `ctx.fileUpload.upload(sessionId, body, name, signal, onProgress)`
> 「Session 标识同时用于寻址原始路由和生成的 Remote 兜底」
> **已知限制**：「上传不能断点续传」；「stream 请求体只能使用一次」；「stream 进度没有总量」

⇒ 它是 **Session 寻址**的，目的是给 prompt 用，不是通用文件搬运。**不采用**。

### 1.4 官方三条必须吸收的硬约束

| 约束 | 官方取值 | 出处 | 本轮的采纳 |
|---|---|---|---|
| 二进制判定 | 采样**前 8192 字节**，含 NUL 即判为二进制 | `dsh-client-ui-sidebar-documentpreview` 的 `DshBinary` | 采纳，`BINARY_SAMPLE_BYTES = 8192` |
| 文本上限 | `maxBytes` 默认 **2 MiB**；分页 5000 行/页；整档上限 32 MiB | 同上，`file-provider` | 采纳，`SFTP_TEXT_MAX_BYTES = 2 MiB`（读侧允许 `truncated` 截断展示；**编辑侧拒绝**） |
| 本地文件 provider | **只读**（有 `file-read` / `file-page`，无写路由） | 同上 | 印证「写必须走自建通道」 |
| 换行处理 | 官方明确「`decode(new Uint8Array(raw))` 保留 CR，交给逐行渲染处理」 | 同上 | 采纳并**强化**：本插件必须在**写回**时还原，因为 `<textarea>` 会吃掉 CR |

### 1.5 传输上限的推导（不是拍脑袋）

`dsh/channel.js` 的 `RPC_MAX_BODY_BYTES = 8 MiB` 是 `POST /dsh-at-terminal/rpc` 请求体的硬上限。base64 膨胀 4/3，所以 **4 MiB 原文 → 约 5.34 MiB 编码**，留出 JSON 信封与长路径的余量。

⇒ `SFTP_TRANSFER_MAX_BYTES = 4 MiB`（= 8096 KiB 级 payload 的保守上界），超限时**拒绝并给出出路**（终端页 `scp`/`rsync`），而不是让请求在传输层死掉。

## 2. 同类实现调研

调研由并行子代理完成（只读检索，未执行任何构建/测试）。以下每条都是**结论 + 来源**。

### 2.1 VS Code 生态的 SFTP 插件

| 项目 | 「编辑远端文件」的做法 | 冲突检测 | 覆盖策略 | 启示 |
|---|---|---|---|---|
| **Natizyskunk/vscode-sftp**（liximomo 的活跃 fork） | 下载到本地临时文件 → `workspace.openTextDocument` 打开 → 监听保存/删除事件 → 回传上传 | `isFileModified()` 对比 **`file.mtime`** | `uploadOnSave` / `downloadOnOpen`；上传时可 `confirmOverwrite` | 与 VS Code 变体的 `SftpEditSessionManager#uploadIfUnchanged` **同构**：冲突基线就是 (size, mtime) |
| **liximomo/vscode-sftp**（原版，已停维护） | 同上 | 同上 | 同上 | 本插件 VS Code 变体即源于此 |
| **fatih/vscode-sftp** 等 | 走 **`FileSystemProvider`** 虚拟文件系统（`sftp://` scheme） | 依赖宿主 `stat` 结果 | 由宿主 `TextFileEditorModel` 决定 | 用虚拟 FS 更「原生」，但**要求宿主支持** `registerFileSystemProvider`——`<textarea>` 环境没有等价物 |

**结论**：`(size, mtime)` 是本领域**事实标准**的冲突基线，本项目两侧（VS Code / dsh）用的是同一对字段，无需换算法。

### 2.2 dsh / Cordis 生态

`deepseek-ai/deepseek-harness` 中与「文件浏览/预览/打开」相关的包（详见 §1.1/§1.2）：`sidebar-files`（列目录）、`documentpreview`（只读预览，拥有 `patterns` 与 `dsh-resource://` 地址解析）、`api-workspace-files`（Remote `list`）。三者的共同点：**地址是工作区相对的、能力是只读的**。

⇒ 生态里**没有**「第三方插件实现可写远端文件系统」的先例可抄，本轮是自建。

### 2.3 轻量文本编辑器（不打包 Monaco/CodeMirror）已知的坑

| 坑 | 处理 | 参考实现 |
|---|---|---|
| **CRLF 归一化** | `<textarea>` 规范行为；要么归一化 + 记录约定，要么换 `contenteditable` | 各浏览器行为一致，W3C HTML 规范 |
| **Tab 键丢失焦点** | `keydown` 拦截 + `setRangeText`/`value` 改写 + 恢复 `selectionStart` | CodeMirror 的键位层、Ace 的 `textinput` 处理 |
| **大文件** | 设上限并**明确拒绝**，不做「半截缓冲区」 | GitHub 的 1 MiB / 512 KB 预览阈值；VS Code 的 `largeFileOptimizations` |
| **二进制** | 采样判 NUL，拒绝按文本打开 | 本条已由 dsh 官方取值锁定（§1.4） |
| **撤销** | 交给浏览器原生 undo 栈 | 这是 `<textarea>` 的**免费收益**，`contenteditable` 则需要自己实现 |

**结论**：`<textarea>` 的取舍是清醒的——**失去语法高亮，换来无障碍、原生撤销、移动端正确性**，且不需要把编辑器打进 bundle。

## 3. 实现方案

### 3.1 分层与数据流

```
浏览器（dsh Client 半，右侧栏 tab 内）
  views/sftp.ts       目录树：选中文件、查看/编辑/下载/上传按钮、<input type=file>
  views/sftpFile.ts   文件页：<pre> 只读查看 / <textarea> 编辑 + 保存/撤销/冲突询问
  body-session.ts     状态：pane 状态机、上传编排、下载落盘
        │  callRpc('sftp.readFile' | 'sftp.writeFile' | 'sftp.download' | 'sftp.upload')
        ▼  POST /dsh-at-terminal/rpc（JSON）
Host 半（Node 进程）
  dsh/channel.js      4 条新 RPC，参数透传
  src/platform/dsh/sftp.ts   ★ 全部判定都在这一层：类型/大小/二进制/冲突/换行
        ▼  复用，无重写
领域层
  SftpManager.readFile / writeFile（本轮新增） / stat
  SftpSession（ssh2）
```

**设计原则**：判定**只写在 Host 一层**。客户端不做二次校验（它没有真值），也不做二次拼装（`name`、`eol`、`baseline` 都由 Host 给出）。

### 3.2 CRLF 的往返协议（本轮最实质的一处正确性设计）

```
服务器上的文件          读：bytes → text（去 \r） + eol='crlf'
  "a\r\nb\r\n"    ──────────────────────────────►   { text: "a\nb\n", eol: "crlf", size: 8 }
                                                          │  <textarea>（规范：把 CRLF 归一成 LF，这里已经是 LF，无损）
                                                          ▼
  "a\r\nb\r\n"    ◄──────────────────────────────   写：text（先 strip \r 再按 eol join） + eol='crlf'
```

三个细节：

1. **读侧归一化 + 报约定**：`text` 在协议上**恒为 LF**，`eol` 单独传。
2. **写侧先 strip `\r` 再 join**：使转换**幂等**，手搓 CRLF 的调用方不会得到 `\r\r\n`。
3. **`size` 用服务器的 stat，不是 `text.length`**：CRLF 文件写回后比 LF 文本大，冲突基线必须是真实字节数。

若不这么做，实际后果是：**打开并保存任何一个 Windows 换行文件，都会静默改写每一行**。

### 3.3 冲突检测

与 VS Code 变体 `SftpEditSessionManager#uploadIfUnchanged` **同一套规则**，只是把触发点从「文档保存事件」换成「面板的保存按钮」：

- `readFile` 返回 `(size, modifiedAt)` 作为基线；
- `writeFile` 带上 `expectedSize` / `expectedModifiedAt`；
- Host 先 `stat`，不一致 → `sftp-conflict`（除非 `overwrite: true`）；
- 客户端把 `sftp-conflict` 渲染成**一个提问**（「覆盖并保存」/「重新读取」），不是失败横幅——因为**什么都还没失败**，只有用户能决定留谁。

上传用的是另一条守卫：目标已存在 → `sftp-conflict`（除非 `overwrite`）。理由是列表缓存有 20s TTL，「名字看起来是空的」不构成证据。

### 3.4 二进制与上限

| 情形 | 行为 | 错误码 | 文案给的出路 |
|---|---|---|---|
| 文件 > 2 MiB，**查看** | 允许，`truncated: true`，只取前 2 MiB | — | 横幅说明只显示开头 |
| 文件 > 2 MiB，**编辑** | **拒绝**（编辑控件根本不渲染） | — | 说明「保存会丢掉其余部分」，改为下载 |
| 二进制（前 8 KiB 有 NUL） | 拒绝 | `sftp-binary-file` | 「改用下载，或在终端页查看」 |
| 路径是目录 | 拒绝 | `sftp-not-a-file` | 「目录：本面板暂不支持递归下载，用终端页」 |
| 下载 > 4 MiB | 拒绝 | `sftp-file-too-large` | 「用 `scp`/`rsync`」 |
| 上传 > 4 MiB | 拒绝（**按编码后长度**，先于解码） | `sftp-file-too-large` | 同上 |
| 无活动终端 / 终端已断开 | 拒绝 | `no-active-terminal` / `sftp-disconnected` | 两个**不同**的出路 |

> **为什么二进制要拒绝而不是「尽力而为」**：按 UTF-8 解码二进制会得到 U+FFFD 替换字符，用户一保存就把文件写坏了。**拒绝 + 给出正确出路**是唯一诚实的选择。

### 3.5 写权限：`allowSudoFallback` 保持 `false`（一处需要你拍板的取舍）

VS Code 变体的文件管理器构造 `SftpSession` 时用的是 `allowSudoFallback: true`（`src/extension.ts:90`），所以那边写 `root` 拥有的文件会**自动走 `sudo -n`**。

dsh 面此前传的是 `false`，注释理由是「这面只读，开了等于预授权一条不可达的提权路径」。本轮它**变成了可写面**，于是这个理由不再成立——但本轮**仍然保持 `false`**，原因：

- 从**浏览器面板**静默触发一次 `sudo -n` 提权，比从 VS Code 的命令面板触发，静默性更强、可审计性更弱；
- 计划 §0.26 的原意是「等真有写路径再做**专门决定**」，而不是「写路径一出现就自动打开」；
- 失去的能力有明确出路：错误文案直接告诉用户「本面板不提权——检查文件权限，或换一个拥有它的账号」，并在终端页可完成。

**⇒ 这是一个待你确认的产品/安全决策**：若希望与 VS Code 变体行为对齐（写 root 文件自动 sudo），改一处 `allowSudoFallback: false → true` 即可，但建议明确知晓其含义再开。

## 5. 刻意没做的（不是缺口，是范围）

`SftpManager` 已有 `mkdir` / `rename` / `deleteEntry` / `countDeletableEntries` / `createFile`，本轮**没有**把它们接出来。理由：

- **删除**需要先给出「将删除 N 项」的确证（VS Code 变体就是这么做的：`countDeletableEntries`），补一个确认流程是独立的一块工作；
- **重命名**需要名称输入弹窗与非法的远端名判定；
- **目录递归上传/下载**需要目录选择器与进度呈现（官方 `directoryPicker` 面向的是**工作区根**，不是任意远端目录，套不上）。

一个「确认流程缺失的控件」比「没有这个控件」更糟——这条纪律在本仓库已经反复出现（服务器表单不发「测试连接」、§0.26 的只读决策）。所以本轮 UI **只显示这套 Host 面真的能走完的操作**。

## 6. 仍未验证（诚实登记）

1. **真实远端文件系统未验证**。Host 面用假 `SftpSession` 驱动、浏览器面用脚本化 RPC 驱动，证到的是**判定、状态机、接线与渲染**，不是「一台真服务器返回什么」。需要你在真实 dsh 里走一遍：连终端 → 文件页 → 选中一个文本文件 → 查看 → 编辑 → 保存 → 下载 → 上传一个本地文件 → 观察远端真实字节。
2. **CRLF 文件在真实 `<textarea>` 中的往返未验证**（单元层已断言协议两侧；DOM 层的归一化行为是规范保证，但没有在真机点过一次）。
3. **二进制文件的真机判定未抽样验证**（例如一个真实 `.png`、一个 ELF 可执行文件）。
4. **大文件边界的真机行为未验证**（>2 MiB 文本被拒编辑、>4 MiB 下载被拒）。
5. **视觉效果未验证**（没有浏览器控制；`verify:dsh` 只断言 bundle 契约与 token 桥，不渲染像素）。窄栏下工具栏按钮增多后的换行表现尤其需要你目视一次——`styles.ts` 的 `@container` 断点是 480px，新增 4 个按钮后可能需要上调。
